# Benchmarks

The committed benchmark report the v0.1 definition of done asks for
([END_GOAL.md](END_GOAL.md)): the reference profile the load evidence runs on, how
the scenarios seed their data, the final stored run for every load case L01 to L14
in [modules/17-verification.md](modules/17-verification.md), the commands that
reproduce them, and an honest account of what the numbers do and do not prove.

Every number below is quoted from a stored artifact in `perf/results/`; the file
names are the citations. The case table is generated by
`scripts/benchmark-report.sh` from `perf/results/history.jsonl` (its output is
pasted verbatim), so it can be regenerated when new evidence lands.

## Reference profile

### The machine

All evidence cited here ran on the one development machine the artifacts record
as `apple-m2-pro-12c`: an Apple M2 Pro laptop, 12 cores, 32 GB of memory, Darwin
27.0.0. One machine does everything: the release-built server under test, the
whole local stack in Docker and the k6 load generator share the same 12 cores,
and whatever else the laptop was doing shares them too.

These are laptop numbers: evidence about the code, never a production capacity claim
(D-018). The spec's reference profile in
[modules/17-verification.md](modules/17-verification.md) (a sized API host, a worker
host, a PostgreSQL host and a separate load generator) has not been run; bringing it
up and rerunning this matrix there is open work.

### The stack

`deploy/compose.yaml`, every image pinned by tag and digest (D-017): PostgreSQL
18.6, Valkey 9.0.6, Garage 2.5.0 and Keycloak 26.8.1, all bound to 127.0.0.1. The
measured process is a `cargo build --release` `colophon-server` bound to its own
loopback port, logging WARN-and-above JSON. Every artifact cited records
`topology` as one server, no balancer, and `k6` v2.3.0. `postgres-trouble` is the
one shaped differently: the API runs `--role api` and a second process runs
`--role worker`, so the scenario's SIGKILL takes the outbox down without taking
the API with it.

`scripts/load.sh` sets three things so a run measures its case rather than an
accident of the defaults: per-address, per-credential and delivery rate limits
are lifted to never refuse for every endpoint except `spike`, which deliberately
keeps the real delivery limiter (`COLOPHON_RATE_LIMIT_DELIVERY=1000/2000`) because
shaped 429s are what L06 measures; `stampede` gets `COLOPHON_CACHE_TTL_MS=4000`
and `COLOPHON_CACHE_JITTER_MS=0` so every cached entry expires on a burst
boundary; and the server's file-descriptor ceiling is raised to 16,384, because
macOS's 256 default once made a run measure the OS instead of the code.

### The dataset

There is no shared fixture corpus and no spec-D1 dataset in these runs. Each
scenario's `setup()` signs in through the real Keycloak login form as `dev-owner`,
the administrator `scripts/migrate.sh` bootstraps on the development realm, creates
a fresh project (slug `k6-<run>`), then builds its own corpus through the same HTTP
API a client uses: entry creates carrying `Idempotency-Key`s, or the bulk import
endpoint in its own 512-item chunks, then publishes through changesets so that
`/content/v1` has a generation to serve. Keys carry `Date.now()`, so the corpus
shape is fixed but every run starts a new project; row-level security keeps
earlier runs' leftovers from ever becoming today's reads.

Corpus sizes in the cited runs, read from the scenario files: `smoke` 4 articles;
`warm-baseline` 20 articles across four releases, one entry unpublished;
`cold-cache` a 2,048-entry published corpus; `stampede` 100 posts in each of two
projects; `mixed` a 400-article corpus; `spike` 100 published entries;
`noisy-agent` an article pool per project sized off the VU counts; `cdn-warm` 200
entries; `media-load` 64 articles plus ~11.5 MB PNG uploads; `cache-down`,
`postgres-trouble` and `purge-trouble` about 20 published articles each plus
their own wiring; and `import-scale` builds its 10,000 records during the run
itself.

The spec's dataset D1 (module 17: three isolated projects, 100,000 entries across
ten collections each, three revisions per entry, 10,000 asset records, realistic
reference and locale distributions) is owed with the reference-profile hardware.

## The evidence runs

A stored run is `perf/results/<ISO-date>-<endpoint>-<scenario>-<machine>.json`,
indexed in `perf/results/history.jsonl`. Each records the commit (and whether the
tree was dirty), the machine, the k6 version, request counts and a latency
distribution, database transactions during the run, the server's WARN/ERROR lines
outside any injected-fault window and, for the runs whose gates name them, RSS, CPU
and Postgres-connection samples. A scenario's own verdict lands in the record as an
`lNN` object it computes itself; `scripts/load.sh` fails the run on `held: false`
and stores the file either way, so the failed iterations sit in the store beside
the held run they preceded.

and L17 belong to milestone S and are outside this matrix.

### L01, smoke: held

- Command: `scripts/load.sh smoke throughput`
- One signed-in virtual user paces the whole loop a user walks: reads, If-Match
  saves, reads of the exact revision saved, publishes (each release must land a new
  id and generation +1), pinned delivery reads and the calls a draft API must refuse
  anonymously. Stored: 139 requests, 242/242 checks, 0 failures; the counted steps
  were 54 reads, 12 saves, 12 revision reads, 4 publishes, 8 delivery reads and 4
  refused anonymous calls. The whole run fits in under ~46 s at its pace; the spec's
  five-minute window for L01 is longer than the stored evidence, so the walk is held
  but noted as short rather than stretched.
- Two earlier iterations the same evening stored `l01` `held: false`
  (`...T203712Z-`, `...T204029Z-`): a publish step broke, then a run finished a
  step short.

### L02, warm read baseline: partial, the 30-minute run is owed

- Command: `RATE=400 DURATION=90s scripts/load.sh warm-baseline steady`
- Stored: 36,063 requests at 398/s for 90 s, p95 3.8 ms, p99 6.9 ms, 0 failures;
  cache share 99.9% hits (32,378 hit, 19 miss, 19 coalesced, 1 bypass); server RSS
  under 40 MB, CPU under 14%, Postgres connections 29; 40,427 database transactions.
- Why partial: the case asks for 300/s for 30 minutes with every five-minute
  window's p99 inside the warm gate. The stored run is 90 s, so only window w0
  carries data (p99 6.6 ms); w1 to w7 are zeroed. The `l02` object says so itself
  (`run_seconds: 90`); the duration gap is the report's to keep visible, not the
  gate's to hide.

### L03, cold cache: held

- Command: `TOTAL=30000 scripts/load.sh cold-cache throughput`
- 30,000 iterations of one read each over a 2,048-entry corpus, every key unique:
  30,095 requests at ~1,017/s, p95 62.1 ms, p99 68.2 ms. Every read was a real
  origin fill: 24,029 `miss`, 5,971 `bypass`, and 0 `hit`, 0 `coalesced`, 0 errors;
  the cold arm's own p95 was 62.2 ms and p99 68.6 ms, inside the 300/750 ms cold
  gate; 88,766 database transactions (~3 per request); server RSS under 39 MB, CPU
  peak 68.5%.
- Two earlier iterations stored `held: false` (`...T210606Z-`, `...T210727Z-`).

## What the numbers prove and what they do not

**They prove behaviour, on this machine, at those commits.** That a cold read is a
real Postgres fill and nothing is quietly served from cache. That a thousand callers
at expiry coalesce into 50 fills instead of 22,000. That an over-quota agent is
shaped into honest 429s while the editors beside it stay within twice their own
baseline. That a dead cache answers `degraded` and bypassed fills, a dead database
answers `not_ready` and honest 5xx, and neither loses an acknowledged write nor
serves a stale `hit` to fill the silence. That a failing purge sink means pending
evidence, never false success. The `lNN` objects count the behaviour itself (fills,
coalesced waiters, refusal codes, `/readyz` transitions, per-job retry gaps,
observed generations), so a green row is an assertion about what happened, not only
about how fast it happened.

**They do not prove capacity.** One laptop ran the server, the stack and the
generator together; different hardware draws different curves and these numbers say
nothing about it. Durations are development-length: tens of seconds to a few
minutes, several deliberately under the windows the spec states (L01's five minutes,
L02's thirty, L11's five; L02 and L07 are the openly owed cases and the shorter
stored runs of L01 and L11 are noted here rather than hidden). The dataset is a
per-run handful of projects and entries, not the spec's D1. Every cited run was
made on a dirty working tree during the D-127/D-128 sessions, so "the commit" is
each artifact's base plus its uncommitted diff. And `held` is the scenario's own
computed verdict: the k6 thresholds alone once passed a run whose `l06` recovery
gate missed (`2026-11-04T211044Z-spike-throughput-apple-m2-pro-12c.json`), which is
why the verdict, not the threshold line, is what this report counts.

Two machinery gaps found while writing this report, recorded so they are not
discovered later: throughput-mode results keep `params.total` and `vus` but not the
effective `RATE`, `DURATION` or scenario env overrides, so several run shapes above
are derived from the counters and marked ~; and the results index does not record
why a `held: false` run failed, only the `lNN` object with the gate that missed,
which is enough to diagnose but worth knowing when reading the store.

## The failed iterations in the store

The same evening's earlier attempts are kept beside each held run; the store is an
index of tries, not a highlight reel. Counting the L-case files: `smoke` twice
(20:37, 20:40), `stampede` twice (20:44, 20:46), `cold-cache` twice (21:06, 21:07),
`spike` twice (21:10, 21:12), `cdn-warm` once (21:14), `media-load` once (21:19) and
`import-scale` twice (21:22:06, 21:22:26) stored `held: false` before their held
runs, and `import-scale` (21:22:42) and `cache-down` (19:23) each have a second held
run behind the cited one. Nothing was deleted; `history.jsonl` lists them all.

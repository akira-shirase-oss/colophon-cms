## Breaking changes

Nobody but the maintainer runs Colophon yet, so these are the places where something changed shape between steps,
for anyone following `main` step by step.

### Public answers may be cached for up to 30 seconds (step 3.1)

- **Who is affected:** sites, proxies and CDNs that read `/content/v1`.
- **What changed:** answers were `no-store` (D-045). Now they carry `Cache-Control` that lets a shared cache keep a
  latest answer for 30 seconds and a pinned one for 300, with strong ETags (304 on a match), `Cache-Tag` for purges and
  `Colophon-Cache` (D-048).
- **What to do before upgrading:** if a CDN sits in front of `/content/v1` and must change at once, add it as a CDN
  website connection (step 3.2), whose purges cover every release; otherwise expect up to 30 seconds.

### An article taken down is gone at every release (step 3.2)

- **Who is affected:** sites that read pinned generations.
- **What changed:** a pinned read used to return exactly what was published then. Once an entry is taken down, a read
  of it answers 410 `gone` at every generation, older ones included, and is never cached; lists leave it out at every
  generation. Publishing it again serves it from its new release only (D-049).
- **What to do before upgrading:** treat 410 as removed.

### The Studio looks and is laid out differently (step 3.5)

- **Who is affected:** people who use the Studio, and anything that drives its pages.
- **What changed:** the Material 3 look of step 0.7 is gone (D-053, then D-056, superseding D-011, D-024 and D-025).
  Website connections moved into Settings, and new entries and publish requests open in dialogs.
- **What to do before upgrading:** nothing; the API and stored data are unchanged.

## Highlights

**Is it on the website?** Every release carries one label: *Published in CMS*, *Website update pending*, *Verified at
N locations*, or *Needs attention*. "Verified" always says at how many locations, because a check sees one address at
one moment from one place. A website connection can check the site: it fetches an address, looks for the release's
marker, and keeps every look as evidence, which the release's receipt shows (D-051).

**Taking it back, and a cache that can't serve the wrong thing.** Taking an article down goes through review like
any other publish request, and afterwards the origin refuses it at every address, historical ones included; a CDN
connection purges what changed, and a skipped purge is covered by the next (D-049, D-050). Public answers are cached
in Valkey under keys that name their release, and the release is always read from PostgreSQL first, so a stale cache
can't bring an older release back; when the cache is down, reads go to PostgreSQL (D-048).

**A website built from one release, and a Studio designed for it.** The reference site reads one release with every
read pinned to it, marks every page with it, and goes live with one atomic rename; an older release can never replace
a newer one (D-052). The Studio got its own design system, title search, entry states, version comparison and review
diffs (D-053, D-056).

## Known issues and limits

Not done yet from P3's proof gate ([ROADMAP.md](../ROADMAP.md)): the load cases L01 to L03, the mixed-release
checker, the simulator's cache and delivery faults, and the first public demo, all in step 3.8. From the decisions'
impact columns ([DECISIONS.md](../DECISIONS.md)) and the step history:

- The reference site runs locally only: hosting it is the maintainer's decision (O-012). It has no feeds, sitemaps or
  images yet (P4), and its `/colophon` page names the release but not its receipt (D-052).
- Receipts say *verified at 1 location*: one worker runs one location by default, and a probe sees one address at one
  moment, not every page or every CDN edge (D-051).
- Taking something down waits for a reviewer: there is no emergency path yet. Copies already in CDNs, browsers and
  readers' hands can't be recalled by the origin (D-049).
- Purge requests carry no authentication yet: only the fake CDN in the tests receives them, and the Cloudflare adapter
  isn't built. *Accepted* is the CDN's word only, and a purge that fails for good leaves copies until they expire, 30
  seconds for latest answers and 300 for pinned ones (D-050).
- Single-flight is per process, so several API processes may each fill a key once; every public read still makes one
  small PostgreSQL read for its release; there are no locales in cache keys yet (D-048).
- Saves slow down as the idempotency records grow: on a local database grown to 5 GB, saves ran 3.5 times slower than
  on a fresh one (step 3.5). Storing those records for locality and cheap retention is planned in milestone R.
- The Studio still shows internal words, "changeset" among them, until step 3.7 applies D-059's glossary.
- Delivery still addresses projects by id, and every published project is public (D-045).

## Verify the download

There is no download before v0.1: Colophon is built from source. To check that a checkout contains everything P3 has
merged so far:

```sh
git merge-base --is-ancestor 065e614 HEAD && echo "P3 so far is in this checkout"
```

Checksums, signatures and an SBOM come with the first release (module 19, P6).

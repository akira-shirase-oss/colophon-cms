# Colophon P2 — review exactly what goes live, and publish it once

Released 2026-10-26: the day its last step, 2.4, merged into `main` (`c38ec47`). Colophon is pre-release, so there is
no download and no version number; here "released" means the milestone's proof gate passed with its evidence stored.
With P2, editors gather entries into a publish request, a reviewer approves exactly the versions on screen, and
publishing makes one numbered release that readers get through the public API. Your website is told about each release
even if the server crashes halfway, and a release that a newer one overtook is never sent.

## Breaking changes

Nobody but the maintainer ran Colophon during P2, so these are the places where something changed shape between
steps, for anyone following `main` step by step.

### Two new database roles (steps 2.2 and 2.3)

- **Who is affected:** anyone with a PostgreSQL set up before step 2.2, including a local stack.
- **What changed:** public delivery reads as `colophon_delivery`, which can't read drafts (D-045), and the worker runs
  as `colophon_worker` (D-046). Migrations 0008 and 0009 grant to them.
- **What to do before upgrading:** create both roles as `deploy/postgres/roles.sql` does; on the local stack, run
  `scripts/stack.sh up` once more, which is safe to rerun ([deploy/README.md](../../deploy/README.md)).

### `changesets` and `releases` are reserved names (step 2.1)

- **Who is affected:** a project with a content type named `changesets` or `releases`.
- **What changed:** those names belong to Studio pages now, so a content type can't take them (`reserved_slug`),
  as `members` and `settings` couldn't from step 1.7.
- **What to do before upgrading:** rename such a content type.

## Highlights

**Approve the exact change, publish it once.** A publish request pins the exact versions of the entries in it and is
identified by a hash of them; an approval counts only while that hash holds, so any edit afterwards needs approving
again (D-044). Publishing commits one release in one transaction, numbered from the release the publisher saw: two
people publishing at once can't both win (D-045). Publication history is a set of non-overlapping intervals, so any
past release can be read exactly as it was through `/content/v1`.

**Work that survives a crash.** A release and the jobs that announce it commit together (a transactional outbox).
The worker claims jobs under leases and posts with a stable idempotency key, only to public `https` addresses, and
never sends a release that a newer one has overtaken (D-046). Crash tests kill the worker after it announced and
before it recorded that (F03), and run an old delivery after a newer release (F05).

**Killing it on purpose.** A simulator of publishing, with workers that crash at any step and a network that loses,
duplicates and refuses, must catch eight planted bugs; modelling the worker found that two announcements could be in
flight to one destination at once, so a slow network could deliver release N after N+1. A real-process crash loop
kills the server and worker with SIGKILL at random moments and checks that nothing acknowledged was lost, doubled or
delivered out of order (D-047).

## Known issues and limits

Not built from P2's plan ([ROADMAP.md](../ROADMAP.md)): the CLI's `release validate`, `publish` and `status` and
`jobs inspect` commands, and the generated SDK with its pinned-read helper. From the decisions' impact columns
([DECISIONS.md](../DECISIONS.md)):

- Publish requests can't include media yet, because no assets exist; the view shows the newest 100 reviews (D-044).
- Delivery addresses projects by id, every published project is public (no private delivery yet), and answers are
  `no-store` until P3's cache (D-045).
- A webhook receiver must deduplicate by `Idempotency-Key` to get exactly one effect. Announcements aren't signed yet:
  an HMAC header comes with destination secrets. Per-destination and per-project concurrency limits aren't enforced;
  supersession keeps at most one announcement per destination worth sending. The worker polls; wake-ups are still an
  open decision (O-010). `--role worker` still serves the API too (D-046).
- A worker paused, not killed, for longer than its lease could still send late: receivers should treat
  `Colophon-Generation` as the order and drop older releases. The crash loop kills the API and worker together, as one
  process; the simulator models PostgreSQL and the network rather than running them (D-047).
- On the reference laptop, publishing at 100 publishes a second fell behind; the steady target is 40 a second, from
  END_GOAL's editorial write budget (p99 700 ms).

## Evidence for this milestone

The proof gate ([ROADMAP.md](../ROADMAP.md)): F03 and F05; two concurrent releases on one base can't both win; the
simulator covers the outbox; the first crash loop. It was checked after step 2.3 and completed by 2.4.

- **CI:** passed on `2831ef2`, the push with 2.1 and 2.2 (GitHub Actions run 40324565689), and on `070415e`
  (40329916852). On `c38ec47`, P2's last merge, every job passed, the crash tests and the crash loop included, except
  the load smoke, which was cancelled when the next push arrived (40355279572). That next push, `0512497`, a
  Studio-only fix, failed CI's members load smoke (p99 373 ms against 200; 40357605434); the one after it, `e5c874a`,
  passed (40362641000).
- **Fault cases:** F03 (the worker killed after announcing: the next attempt sends again with the same key, and the job
  succeeds after two attempts) in `crates/colophon-server/tests/faults.rs`; F05 (a release superseded by a newer one is
  never sent) in `crates/colophon-server/tests/worker.rs`; F01 and F02 still pass. Two releases on one base can't both
  commit, in `crates/colophon-db/tests/releases.rs` and end to end.
- **Simulator:** CI sweeps 1,000 seeds of the publishing scenario and 2,000 of the editing one. All eight planted
  publishing bugs are caught within 200 seeds; 20,000 clean seeds held every invariant on the laptop; seed 449, which
  found a bug in the model's lease check, is a regression test.
- **Crash loop:** `crates/colophon-server/tests/crash_loop.rs`, 12 kills per CI run. Its first full run: 524 releases
  acknowledged and checked, 9 requests cut off by a kill and sent again, 453 announcements received; nothing lost,
  nothing doubled, nothing out of order.
- **Load**, all on `apple-m2-pro-12c` (Apple M2 Pro, 12 cores, 32 GB), k6 on the same machine:
  - publish requests: [1,000,267 at 1,461/s, p99 58.9 ms](../../perf/results/2026-10-26T040643Z-changesets-throughput-apple-m2-pro-12c.json),
    [steady at 1,000/s, p99 15.1 ms](../../perf/results/2026-10-26T040751Z-changesets-steady-apple-m2-pro-12c.json);
  - public delivery: [1,000,058 anonymous reads at 2,650/s, p99 31.3 ms](../../perf/results/2026-10-26T043905Z-delivery-throughput-apple-m2-pro-12c.json),
    [steady at 2,000/s, p99 9.3 ms](../../perf/results/2026-10-26T044011Z-delivery-steady-apple-m2-pro-12c.json);
  - publishing with the worker: [steady at 40 publishes (209 requests) a second, p99 18.9 ms](../../perf/results/2026-10-26T122940Z-publishing-steady-apple-m2-pro-12c.json).
- **Missed and failed runs kept:** publishing,
  [1,000,201 requests at 680/s, p99 387 ms against a 250 ms target](../../perf/results/2026-10-26T052935Z-publishing-throughput-apple-m2-pro-12c.json)
  (none failed; it led to the worker's own database pool);
  [steady at 100 publishes a second, which fell behind](../../perf/results/2026-10-26T053052Z-publishing-steady-apple-m2-pro-12c.json)
  (p99 2.3 s, 931 starts dropped); and
  [a million-request run that didn't finish clean](../../perf/results/2026-10-26T130045Z-publishing-throughput-apple-m2-pro-12c.json)
  (874,279 requests in the 30-minute cap, 82 failed, on a database grown to several gigabytes).

These are evidence about the code on one laptop, not a capacity claim for production hardware (D-018).

## Verify the download

There is no download before v0.1: Colophon is built from source. To check that a checkout contains all of P2:

```sh
git merge-base --is-ancestor c38ec47 HEAD && echo "P2 is in this checkout"
```

Checksums, signatures and an SBOM come with the first release (module 19, P6).

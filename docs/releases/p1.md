# Colophon P1 — write and save without ever losing an edit

Released 2026-10-26: the day its last step, 1.8, merged into `main` (`2652f43`). Colophon is pre-release, so there is
no download and no version number; here "released" means the milestone's proof gate passed with its evidence stored.
With P1, people sign in, work in projects that can't see each other, and write entries in the Studio or from the
command line. A save that was acknowledged is never lost, a save sent twice is stored once, and when two people edit
the same entry, neither overwrites the other: the Studio shows both versions side by side.

## Breaking changes

Nobody but the maintainer ran Colophon during P1, so these are the places where something changed shape between
steps, for anyone following `main` step by step.

### Responses moved into `data` (step 1.2)

- **Who is affected:** clients of `/me` and `/api/v1/projects` written against step 1.1.
- **What changed:** a resource is `{"data": …}` and a list is `{"data": [...], "next_cursor": …}`; the request id
  travels in the `x-request-id` header, not the body (D-035).
- **What to do before upgrading:** read the answer's `data`.

### `articles` became an ordinary content type (step 1.5)

- **Who is affected:** anything that relied on `articles` being built in, or on the `invalid_title` error code.
- **What changed:** content types are versioned definitions, and every entry is checked against its collection's
  current one (D-040, superseding D-034's single built-in collection). Every environment starts with `articles` as
  version 1, and an article title that breaks the rules is now refused with `invalid_text`.
- **What to do before upgrading:** nothing for stored content; migration 0003 backfills it. Match on `invalid_text`.

### Roles decide what members may do (step 1.7)

- **Who is affected:** members who aren't owners, and projects with a content type named `members` or `settings`.
- **What changed:** one policy table decides what owners, developers, editors and publishers may do (D-042): writing
  content, changing content types and managing members each need a role that allows it. `members` and `settings`
  name Studio pages, so a content type can't take those names (`reserved_slug`).
- **What to do before upgrading:** give each person the role they need, and rename any content type with a reserved
  name.

### Only administrators create projects (step 1.8)

- **Who is affected:** anyone who created projects before step 1.8, and a local Keycloak started before it.
- **What changed:** creating a project needs an installation administrator (D-043); the first one is made once, from
  a terminal, with `colophon admin bootstrap`. The development realm now fixes its users' subjects.
- **What to do before upgrading:** run `colophon admin bootstrap --subject <your subject>` once (`scripts/migrate.sh`
  does it for the local `dev-owner`), and recreate a Keycloak started before 1.8
  ([deploy/README.md](../../deploy/README.md)).

## Highlights

**A save is never lost and never doubled.** Every save names the version it was made on, so a save made on an older
version is refused instead of overwriting newer work, and every write carries an idempotency key, so a retry gets the
recorded answer instead of saving twice. Crash tests kill the real server before and after the commit (F01, F02) and
check that nothing acknowledged was lost and nothing was stored twice (D-034 to D-036).

**Two editors, one entry.** The Studio saves as you type, keeps unsaved edits on your device, and when someone else
saved first, shows both versions side by side (F04, in two real browsers). A deterministic simulator of colliding
editors, lost answers and crashes found one real bug on its first run: after a lost answer and a reload, the Studio
could store an edit twice. It now resends the unanswered save with its key (D-038, D-039).

**Projects, people and the command line.** Sign-in goes through OpenID Connect, and row-level security in PostgreSQL
keeps projects apart: a project you aren't a member of looks exactly like one that doesn't exist (D-031 to D-033).
Owners invite people with single-use links (D-042), the first administrator is made once from a terminal (D-043), and
`colophon login` signs in from a terminal with a code you approve in the Studio (D-041).

## Known issues and limits

Carried forward from P1's plan, not built ([ROADMAP.md](../ROADMAP.md)): URL names (slugs) and their claims, which
arrive with step 3.6; locales; environments other than `production`; and the generated OpenAPI document (D-027). The
gate's "colliding slugs" check moved with them. From the decisions' impact columns ([DECISIONS.md](../DECISIONS.md)):

- After a database restart, up to one request per idle pooled connection can fail (D-033).
- The Studio keeps unsaved edits on the device for up to 30 days without asking; clearing them on sign-out comes with
  a sign-out control. Merging two versions field by field is later: today you keep one version or the other (D-038).
- Content types have text, rich text, number, checkbox, choice and date-time fields only; images, references and
  lists come later, and so do migrations with plans for changes that would invalidate stored entries (D-040).
- Device sign-in has no per-client rate limit yet. A CLI token acts with its person's full membership rights; scoped
  credentials for scripts and agents are P5 (D-041).
- Invitations aren't tied to an email address, so whoever holds a link can use it; role changes don't yet ask for a
  fresh sign-in; creating an invitation takes no idempotency key; member and invitation lists stop at 1,000 with no
  cursor (D-042).
- There is one administrator; more need a grant flow, planned with project administration. Anyone holding the
  migrator's credentials can still change anything (D-043).
- `/me` lists at most 1,000 projects. The Studio read your role from that list until the fix of 2026-10-26
  (`0512497`, in P3's section of the changelog).

## Verify the download

There is no download before v0.1: Colophon is built from source. To check that a checkout contains all of P1:

```sh
git merge-base --is-ancestor 2652f43 HEAD && echo "P1 is in this checkout"
```

Checksums, signatures and an SBOM come with the first release (module 19, P6).

COMPLETE PRODUCT + ENGINEERING SPECIFICATION
Rust + Svelte CMS
One master document. The full product, end to end.

Use this document only. It replaces the earlier CMS blueprints; no other edition or companion specification is required to understand the defined product scope.
The end goal
A CMS that nontechnical editors can use visually, developers can operate from a terminal, and AI agents can use safely at scale. One Rust engine enforces shared content, permission, migration and publishing rules. Svelte powers the Studio, public website, documentation and reference storefronts.
Product area
Included in this specification
Content and delivery
Schemas, revisions, localization, approvals, scheduling, media, search, public/preview APIs, edge caching and verified publishing.
Interfaces and AI
Studio, CLI, TypeScript SDK, typed agent tools/MCP, AI suggestions, bulk work, permissions and budgets.
Templates and commerce
Blog, business forms/leads, knowledge base, physical/digital commerce, Stripe, stock, shipping/tax configuration, refunds, subscriptions and entitlements.
Engineering and operations
PostgreSQL/Redis contracts, deployment, security, load/failure tests, upgrades, backups, recovery, documentation and open-source maintenance.

Architecture commitments
Rust + Axum + Tokio + SQLx; SvelteKit + TypeScript; PostgreSQL; Redis; object storage; CDN. PostgreSQL owns durable state. Redis and edge caches accelerate eligible public reads. AI and payment providers never bypass the Rust authorization and transaction layer.
How to interpret the plan
The full scope is specified now. Work packages describe implementation order, not separate product versions or missing chapters. Requirements, operating defaults and performance targets are design commitments to implement and verify—not claims that a CMS, security audit or benchmark already exists.
Provider credentials, merchant regions, actual capacity and the executable dependency lock are deployment/validation inputs. Explicit non-goals are listed separately. Software, schema and API version histories remain necessary for safe upgrades.

01 / Product scope and users
One engine, three experiences
User
Primary job
Success signal
Nontechnical editor
Write, improve, preview, approve and publish content.
Publishes a valid article without opening a terminal or asking what cache invalidation means.
Developer
Define schemas, migrate safely, integrate APIs and operate installations.
Sets up the blog from documentation, upgrades it and diagnoses a failed delivery.
AI agent
Discover permitted schemas, prepare bounded changes and report results.
Completes an authorized task without bypassing review, leaking data or exhausting resources.

Target audience and defined product boundary
Acquire developers or small agencies maintaining content-heavy sites; invite their editors into the same projects. Support agent credentials from the beginning, but do not launch three unrelated go-to-market strategies. The reference installation serves one organization with isolated projects and environments. It can be self-hosted or managed for that organization; hostile-tenant open registration is not part of this specification.
Included foundation: projects, basic roles, schema-driven collections, rich text, media images, drafts, revision comparison, preview, review, publish/unpublish, REST delivery, CLI, TypeScript SDK, audit history, durable publication jobs, edge caching and a first-party blog starter.
Also included in this complete scope: business pages and lead forms; scheduled releases and localization; bounded agent workflows; physical and digital single-merchant commerce; subscriptions; shipping/tax configuration; returns and refunds. The detailed contracts appear in this same document. Each module has permissions, migrations, operating limits and failure tests.
Explicit non-goals: arbitrary untrusted native plugins, CRDT live co-editing, GraphQL, active-active multi-region database writes, multi-seller marketplaces, usage-based billing and autonomous production repair. These are excluded product categories, not undefined parts of the promised CMS. The commerce scope provides configured merchant tax/shipping workflows, not a worldwide tax-law engine.
A useful advantage must be demonstrated
Strapi documents releases; Payload documents versions and restoration; Sanity documents CDN delivery. Do not market their absence as our advantage. [R27–R29]
Our hypothesis is that reliable delivery evidence, safe agent operations and approachable tooling reduce setup and investigation work. Validate with comparable tasks, not a feature-count comparison. Templates, a CLI, Rust and an AI button are features; independently demonstrated reliability and trusted integrations may compound into an advantage.
Product acceptance exercise
Give a new developer the README and a nontechnical editor the Studio. Observe setup, drafting, correcting validation errors, reviewing an AI suggestion, publishing, and understanding a deliberately delayed website update. Record completion time and intervention needed. A polished interface that hides an unresolved publication is a failure.

Deployment decision
Prerender the marketing and docs sites. Build Studio as a client-side SvelteKit application served as static assets, with /api routed to Rust on the same origin. This avoids a second backend framework. SPA startup has tradeoffs, so it is limited to the authenticated Studio; public SEO pages are prerendered. [R01, R02]
Node.js remains build tooling, not the CMS business backend. Do not add SvelteKit server actions that directly query PostgreSQL. The first-party storefront prerenders public pages and enhances private cart/account flows in the browser. External consumer applications may use SSR, but all CMS and commerce authority remains behind Rust APIs. Static builds are promoted by the versioned deployment workflow.
Pinning: commit Cargo.lock, rust-toolchain.toml, the package-manager lockfile and container digests. Freeze a tested compatibility set at M0 instead of assuming all newest versions work together. Redis licensing is addressed in section 35.
03 / Architecture and repository
Modular monolith with independently runnable workers
Studio, CLI, SDK and agent adapters call the Rust management API. Thin HTTP handlers authenticate, validate requests and call the same domain services. The public delivery API is read-only and uses published projections only. Workers execute committed jobs; they cannot invent authorization or publication state.
Svelte Studio / Rust CLI / TypeScript SDK / agents
                         |
                 Rust management API
                         |
       Domain rules + authorization + transactions
                         |
           PostgreSQL + durable event outbox
                 |                    |
          Publishing workers     Immutable revisions
                 |                    |
        CDN / site adapters      Public delivery API
                 |                    |
           Delivery evidence     Generation-keyed results

Public read path: reader → CDN → Rust delivery API → Redis cache → PostgreSQL published projection on a miss. Arrows above show responsibilities, not mandatory microservices. Begin with one Rust workspace and one deployable service with a separate worker mode. Split management and public-read processes only when traffic tests justify independent scaling. Never hold a database transaction open while waiting for a model, object store, CDN or Stripe.
Repository structure
apps/{studio,web,docs}/        # SvelteKit frontends

crates/{auth,media,ai,commerce}/
packages/{sdk,ui,content-renderer}/

migrations/                  # Core PostgreSQL migrations
templates/{blog,business,commerce}/
tests/{contracts,faults,security,load,fixtures}/
deploy/                      # Compose, containers, runbooks
docs/{adrs,threat-model,release-policy}/

Ownership and isolation
The domain crate owns invariants; adapters own external protocols. Keep domain independent of HTTP and database drivers. Tests supply clocks, model responses and fault-injecting adapters. Document every externally visible operation and who can authorize it.
Run database and Redis on private networks. Deliver uploads from a separate asset origin, not the administration origin. Separate production and staging credentials, buckets and cache namespaces. Production can use managed infrastructure; the Rust requirement applies to our application code, not to rewriting PostgreSQL, Redis or a CDN.
No premature dependency: reuse design lessons from Service Monitor and the future runner, but begin with a small PostgreSQL-backed job/outbox implementation. Our experimental JavaScript runtime is not a dependency of this product.
04 / Onboarding and project lifecycle
A complete setup path for operators and editors
The installer must finish with a usable project, not a dashboard full of disconnected settings. The default distribution is self-hosted for one organization, with isolated projects and development/staging/production environments. It can also be run as a managed single-organization deployment. Open public registration and hostile-tenant shared hosting are not assumed.
Operator setup
	•	Start the Rust API and worker with PostgreSQL, Redis, object storage and an identity provider. The reference self-hosted sign-in integration uses Keycloak through OIDC; another conforming provider can replace it after contract tests. Keycloak is an infrastructure dependency, not a second CMS application backend. [R37]
	•	Run a one-time, local bootstrap command to bind the first owner to an authenticated issuer/subject. Disable bootstrap permanently after completion. Do not select owners from an unverified email claim.
	•	Configure canonical administration, content, asset and preview origins, TLS, secret references, backup destinations and quotas. cms doctor reports readiness per dependency; Redis may be degraded while authoritative writes remain available.
	•	Create a project, choose locales and a template, review the installation plan, and create its schemas and seed drafts transactionally. Production fixtures must not contain invented customers or testimonial claims.
	•	Invite an editor, run the first draft/preview/publish exercise, test a delivery failure, and run an export/restore drill. Commerce and external AI remain disabled until their own configuration checks succeed.
Editor setup
An invitation is single-use, expires after a configurable period (default 72 hours), and is bound to an authenticated verified identity. The editor sees the project name, role and capabilities before accepting. The initial screen offers Create article, Upload media and Ask AI; it does not expose database or cache configuration. No code is required for normal authoring.
Lifecycle contract
Operation
Required behavior
Rename project
Change the display name; preserve stable IDs, keys and content history.
Clone environment
Copy allowed schemas and content; issue new namespaces. Never copy live payment keys, customer records, sessions, webhooks or sending authority implicitly.
Archive project
Block new writes and jobs; keep history and existing delivery behavior explicit. Archiving does not silently unpublish a live site.
Delete project
Require fresh owner authentication, impact preview and confirmation; revoke credentials, tombstone public data, purge caches, and track deletion completion.
Export or leave
Produce a manifest with content, schema hashes and allowed assets; retain access until the agreed deletion/export process finishes.

Acceptance: a clean installation, owner recovery, expired invitation, environment clone and interrupted template installation all have reproducible tests. Restoring or cloning a project must not restart real payments or notifications.

Make the normal path obvious
The first visit offers an enabled template, a site name, language and brand settings. The Blog template is the first implementation exercise; the full template catalog is defined in this document. The blog template supplies posts, authors, categories, SEO fields and a usable sample website. Advanced schema settings stay under a developer area; the editor starts with Content, Media, Review and Publishing.

Editorial safety and responsiveness
Debounce autosave and send an expected revision. A concurrent save returns a conflict rather than silently overwriting another user. Keep an unsaved local recovery copy only with a clear expiry and consent policy; never imply server persistence before acknowledgment. Leave a page only after confirming unsaved changes or explicitly discarding them.
Use plain error messages with a concrete next action. Do not expose internal job terminology when “Website update pending” is sufficient; preserve a technical detail drawer for developers. Do not hide failures behind an indefinitely spinning button.
Rich text contract
Store versioned Tiptap JSON, not executable HTML or Svelte components. Allow only approved nodes, marks, links and embeds; enforce size and nesting limits in Rust. Use shared renderer fixtures to verify Studio preview and the storefront agree. Server-side validation remains authoritative. Tiptap supports Svelte integration; advanced paid extensions are not assumed to be included in the OSS core. [R03]
Accessibility and validation gate
Target keyboard operation, meaningful focus states, labeled controls, screen-reader announcements, readable contrast, reduced motion and mobile review. Test with actual editors and assistive technology in addition to automated checks.
First usability gate: five representative editors each attempt to draft, preview, accept one AI edit and publish. Proposed target: at least four complete the flow without developer intervention; record the failures and revise the design. This is an experiment, not a usability claim already achieved.
06 / Editorial workflow, localization and preview
One visible workflow for humans and agents
Each localized entry has an immutable revision history. Draft, submitted, changes requested and approved are editorial states; publication is a separate state. Comments and review decisions refer to a revision, not just an entry ID. Publishing a revision does not discard a newer draft.
Review and collaboration
An author submits a changeset containing exact entry/revision/schema/asset hashes. A reviewer compares before/after, requests changes or approves that exact changeset. The default permits a single operator to review their own work, visibly recorded; projects may require a different reviewer. Agents cannot approve their own proposals. An edit, policy change or expired approval forces revalidation. Comments are escaped, permission-checked and retained in audit history.
Concurrent editing uses optimistic revision checks, not silent last-write-wins. A conflict screen preserves the local proposed edit, shows the current server revision and offers explicit merge or discard. Same-document live cursors and CRDT co-editing are outside this defined product; safe multi-editor collaboration is covered by revisions, comments and conflict handling.
Localization contract
Concern
Decision
Identity
One logical entry groups locale variants; each variant has its own slug, draft and publication history.
Fallback
Explicit project policy: none by default. A requested fallback uses only published revisions and labels the resolved locale.
Required content
Required fields are validated per locale; a missing translation never exposes an untranslated private draft.
References
Locale-specific references resolve within the pinned release and declared fallback policy.
Translation AI
Creates a proposed locale revision with source attribution; edits invalidate prior approval.

Preview and site metadata
The UI issues a short-lived capability scoped to project, environment, exact revision set and permitted asset IDs. Default expiry is 15 minutes; the preview server validates it on every protected fetch. Use a separate sandboxed preview origin, no-store, noindex and a restrictive referrer policy. Preview artifacts and private media must never enter public CDN routes, sitemaps or search indexes.
Schemas include title, slug, description, canonical URL override, image alt text and social metadata. Normalize canonical origins against the verified site configuration. A slug change proposes a reviewed redirect; prevent cycles and collisions. Generate sitemaps and language alternates from a single published generation. Robots directives are not an authorization boundary.
Scheduled publishing
Store the chosen local time, IANA timezone, resolved UTC instant and approval hash. Ambiguous or nonexistent daylight-saving times require an explicit choice. At execution, recheck authority, approval, revision hashes and dependencies; edited content blocks rather than silently changing the scheduled release. A delayed schedule is labeled delayed. Cancellation prevents new dispatch but does not undo a release already committed.
07 / Content model and database
Typed rules over flexible content
Use relational metadata plus JSONB content revisions. Do not create arbitrary SQL tables for each collection in the selected architecture. A versioned schema describes field IDs, types, validation, references, visibility and editable roles. Use a constrained, documented JSON Schema-compatible subset, not arbitrary user-executed validation code.
Entity
Important fields and constraints
Project / environment
Organization, project ID, environment ID; production and preview are separate namespaces.
Schema version
Collection ID, version, canonical definition, hash, lifecycle and migration reference.
Entry
Stable ID, project/environment, collection, current draft revision, archived flag.
Content revision
Immutable ID, schema version, structured data, author/agent, base revision, timestamp and hash.
Reference / uniqueness
Typed relation edges and normalized unique claims; project/locale scope enforced in PostgreSQL.
Release / release item

Destination delivery
Release, destination, generation, attempts, evidence, verified-at and terminal/uncertain outcome.
Job / outbox / inbox
Durable accepted work, dispatch leases, deduplication keys and external event receipts.
Asset / audit / credentials
Asset lifecycle and references; append-only audit; hashed tokens and encrypted secret references.

Validation and storage rules
Validate field types, bounded strings, rich-text depth, references, locale, slug normalization and cross-field rules before a revision commits. Referential and uniqueness checks also need database enforcement; API prechecks alone race. Namespace slugs and unique claims by project, environment and locale.
Implement first-class text, rich text, number, boolean, datetime, enum, image, reference and bounded lists. Posts/authors/categories provide the first fixtures. All enabled collections use the same bounded component/schema rules and renderer compatibility tests. Unrecognized fields fail validation by default, not silent data loss.
Query design
Support cursor pagination, selected fields, explicit indexed filters and stable sort keys. Parameterize values and allowlist column/filter names. Default page size 20, maximum 100; no unlimited expansion or raw SQL from agents. Create query-specific indexes after examining representative plans, including project/environment prefixes.
A release changes publication pointers/history, not historical content bytes. Retain referenced revisions while a retained release, draft or audit contract depends on them. Schema and asset deletion must consider these references. Separate commerce state from editorial JSON; orders are not editable documents.
08 / Database invariants and transaction boundaries
Make correctness independent of the interface
All entity IDs are opaque and scoped by organization, project and environment. A user-supplied ID alone never establishes authority. Every write carries an actor, request ID and the active authorization context. The primary database, not Redis, decides conflicting edits, publishing generations, quotas and financial state.
Invariant
Database and service enforcement
Immutable revision
Insert-only revisions; a composite foreign key binds every reference to the same project/environment. Restoring creates a new revision.
Concurrent save
Compare the entry's draft pointer to expected_revision; update the pointer and insert the revision in one transaction. A loser returns 409.
Unique slug
A normalized uniqueness record scoped to project, environment, collection and locale. Draft reservations and published routes have explicit lifetimes.
Single release order
Lock the environment generation row, check base generation, create release/items and advance the pointer with audit/outbox in one commit.
Historical publication
Half-open generation intervals cannot overlap for the same entry/locale. The public projection only includes schema-approved public fields.
Idempotent mutation
Unique actor/scope/key plus request hash; reserve and commit its result with the effect. A different payload conflicts.
Worker ownership
Lease owner, lease expiry and attempt generation are checked by a conditional update before accepting completion.
Commerce uniqueness
Unique merchant/provider/event receipt and order/fulfillment-action key; append-only money and inventory adjustments.

Transaction choices
Use short READ COMMITTED transactions with explicit row locking/conditional updates for identified resources. Multi-row invariants use deterministic lock ordering or SERIALIZABLE transactions with bounded whole-transaction retries. Never retry only the last statement of a transaction that failed serialization. Deadlocks and serialization conflicts are observable; after three internal retries, return a safe conflict/transient error rather than loop indefinitely. [R23]
There is no database transaction across a model call, CDN purge, identity provider, object store or Stripe. Commit an intent/outbox first, execute externally, then persist evidence. For safety-critical actions, cancellation or permission revocation is rechecked before the next external attempt. A previously completed external action cannot be undone by rolling back local SQL.
Retained authority
Reserve pending-job and expensive-operation capacity before acceptance. Do not accept a job merely because it was placed in a process-local channel. RLS is defense in depth alongside application checks; use distinct migration, API, delivery and worker database roles, and test pooled transaction-context reset. Public delivery cannot query draft tables with elevated credentials. [R09]
Migration and testing artifacts
The repository must contain executable SQL migrations, generated OpenAPI schemas and fixture data derived from these contracts. They are implementation outputs, not evidence that this document already contains a running database. Required tests cover two concurrent saves, duplicate submission, cross-project references, generation conflicts, crashed workers and failed transaction commits.
09 / CLI, API and developer experience
The terminal is a first-class interface
The following command names are proposed contracts, not a released executable. cms is a working CLI name.
cms init my-site --template blog
cms dev
cms schema validate
cms schema diff --env staging --json
cms migrate plan --env staging --out plan.json

cms content import posts --file drafts.jsonl --dry-run
cms release create --from changeset.json --json
cms release validate RELEASE_ID --json
cms release publish RELEASE_ID --env production --dry-run
cms release status RELEASE_ID --json
cms doctor --json

One API, no bypass
CLI, SDK and Studio operations pass through the same authorization and transaction services. The normal CLI never requires a production database password. Bootstrap and infrastructure migrations are explicit administrative commands, separated from content editing.
Publish stable /api/v1 management and /content/v1 read contracts. Export OpenAPI and generate the TypeScript client; test generated clients against the server in CI. Schema discovery returns only collections and fields the caller may access. Client validation improves feedback, but Rust revalidates every mutation.
Predictable machine behavior
--json writes a single versioned result to stdout; progress and diagnostics go to stderr. Never prompt in agent mode. Return stable exit categories: success, validation, denied, conflict, transient dependency failure and unexpected internal failure. An accepted asynchronous job returns its ID and polling location; that is not a successful publication.
Mutations accept an idempotency key, operation scope, payload hash and expected revision. A matching replay returns the recorded result; a different payload with the same key conflicts. Retain ordinary keys at least seven days; critical business operations have longer durable uniqueness constraints independent of this retention.
API conventions
Use opaque identifiers, cursor pagination, request IDs, revision ETags and structured field errors. Return 401 for missing identity, 403 for denied action, 409 for conflicts, 422 for invalid content, 429 for throttling and 503 for dependency/capacity unavailability. Prevent identifier probing through a consistent resource-visibility policy.
Document authentication, retry eligibility, limits, errors and examples. The website and docs must distinguish implemented features from the roadmap. Build code examples in CI so a release does not ship documentation for commands that no longer work.

Requests and errors
Mutations require Idempotency-Key for retriable creates and an expected revision/generation for conflicting writes. Use If-Match for single-resource updates; missing preconditions return 428, a stale revision returns 409 with a safe conflict description. Idempotency scope includes actor, operation and environment. Inputs use UTC RFC 3339 timestamps, integer minor currency units and bounded JSON; provider-specific currency precision is validated rather than assumed to be two decimals.
A successful synchronous response contains data, request_id and the resulting revision. An asynchronous 202 contains operation_id, status: accepted and a polling URL; it never says published or paid. List responses contain next_cursor, applied filters and limits. Errors contain code, readable message, field paths, retryable and request_id; no stack or secret is exposed.
Query and delivery limits
Only documented filters, sorts and projections are allowed. Cursor ordering includes a stable ID tie-breaker; reject cursors from another project or query shape. Enforce page, expansion, size, runtime and cost limits. A pinned-release response includes its generation, ETag and resolved locale. Requesting a revoked or inaccessible historical item cannot bypass current revocation rules.
Parity gate: the generated SDK, CLI and Studio must run the same create/conflict/review/publish scenario and produce equivalent durable records. Contract changes require compatibility tests and a documented deprecation window.
11 / CLI and agent operating contract
Useful commands without dangerous hidden defaults
The CLI uses the Rust API for normal operations. Only installation/bootstrap/database administration commands can access infrastructure directly, and those require a distinct operator mode. Never infer production from the current directory: destructive or publishing commands require an explicit environment.
cms init my-site --template blog
cms login --profile staging
cms doctor --env staging --json
cms schema diff --env staging --json
cms migrate plan --env staging --out plan.json
cms migrate apply --env staging --plan plan.json
cms content create posts --file article.json --json
cms content import posts --file posts.jsonl --dry-run
cms release validate RELEASE_ID --json
cms release publish RELEASE_ID --env production --dry-run
cms release publish RELEASE_ID --env production --approval ID
cms release status RELEASE_ID --json
cms jobs inspect JOB_ID --json
cms integration test DESTINATION_ID --json
cms module enable commerce --env staging --dry-run
cms export --env production --out export-directory

These commands describe the target executable; they have not been implemented by preparing this specification. cms dev may orchestrate local dependencies, but it must never discover and use production credentials silently.
Deterministic behavior
--json writes exactly one JSON result to stdout; logs/progress go to stderr. Long streams use an explicit --jsonl mode with one documented event per line. Agent mode is noninteractive and never waits for a hidden confirmation. Exit codes: 0 success, 2 usage/validation, 3 unauthorized, 4 conflict, 5 transient/unavailable and 6 internal failure. A 202 operation exits successfully with accepted; --wait --timeout reports the eventual state or a wait timeout without cancelling accepted work.
--dry-run validates scope and presents a plan without external side effects. It is not a reservation or a guarantee that state will remain unchanged. Execute rechecks revisions, schema hashes, permissions and approval. Credentials come from a protected profile/keyring or explicit environment injection; token values never appear in process arguments or output.
Agent interfaces
Expose schema discovery, content query, draft create/update, changeset validation, review request, job status and release status as typed tools. Tool discovery filters by current authorization. The CLI and an MCP adapter call identical services; neither is a privileged alternate path. Remote MCP authentication uses the pinned protocol's authorization requirements with audience validation. Local stdio uses scoped credentials supplied by the operator. [R36]
Bulk changes are resumable per item, bounded by the manifest's base revisions and input limits. A client retries the same logical operation key after transport loss; it does not generate a new key for every attempt. A kill switch revokes the account and prevents new work; already completed side effects remain auditable.
12 / Schemas, migrations and importing
Separate three kinds of change
Core SQL migrations evolve our platform tables. Content-schema migrations evolve customer fields and records. Template upgrades evolve a starter's schemas, renderer and configuration. Treat these as separate versioned operations; a template installation is not permission to run arbitrary SQL.
Migration lifecycle
Plan → validate → estimate impact → rehearse on a restored staging copy → authorize → execute bounded batches → verify → finalize. A plan records the source schema hash, target hash, selected environment, expected revisions, operations, estimated affected count and approval identity.
Adding an optional field can be additive. Renaming should preserve a stable field ID. Removing a field, narrowing a type or introducing a required field needs an explicit data transformation and compatibility plan. Never let an AI-produced migration silently remove production data.
Execution rules
Acquire a PostgreSQL migration lock, verify the plan is current, then use expand–backfill–contract. Short transactions, statement/lock timeouts, progress checkpoints and a stop/resume command are required. Large backfills must not hold the editorial service hostage. Some index operations cannot run inside a normal transactional migration; mark and test those steps explicitly.
Preserve compatibility with the current and previous supported application version during a rolling update. Do not promise automatic down migrations for destructive changes. Prefer a tested forward fix; restore a backup only with explicit acknowledgment of the resulting data-loss window.
Nontechnical schema editing
The UI may propose safe field additions and show example data. Developer-controlled collections can be read-only in the schema designer. Both UI and CLI export/import the same schema format; one canonical deployed schema registry prevents Git and UI from becoming conflicting authorities.
Import and exit paths
Begin with JSONL content and asset manifests. Import uses a staging area, source-to-target ID map, idempotent batches, schema validation and a final report. Preserve relationships, slugs, authors and original timestamps where authorized. No partial import is silently published.
The complete import contract accepts native JSONL and normalized Strapi, Sanity and Payload export manifests through adapters. Adapters must map source schemas, references, locales and assets into a dry-run plan; incompatible fields are reported rather than silently dropped. Native import is implemented before the source-specific adapters. Provide complete export of schemas, revisions permitted by retention, published content and asset references. Avoid making data lock-in the moat.
Acceptance cases: interruption halfway through a backfill, stale migration plan, incompatible client, duplicate source IDs, broken references, corrupt assets, schema change during editing and restart during import. Each must produce resumable progress or an explicit failure without hidden publication.

14 / Publishing and release consistency
A publication has more than one state
Editorial: draft → in review → approved. Approval binds to content, schema, asset and release hashes. New edits invalidate it.
Content release: prepared → committed. In one PostgreSQL transaction, recheck authority and base generation; validate the chosen revisions; update publication history; advance the environment generation; record audit and outbox events. A commit is atomic inside this database, not across a CDN or website.
Each destination: pending → dispatched → observed, or retrying / failed / uncertain / superseded. “Published in CMS” and “Verified on website” are separate UI labels. A CDN accepting a purge request is not proof that every edge location has served new content.
Snapshot semantics
Assign release identities as recovery epoch plus monotonically increasing generation per environment. Normal operation keeps one epoch; restore registers a new epoch before serving. The SDK pins both values across related reads so a restored generation cannot collide with old cache data. Publication-history intervals map each entry to the correct immutable revision at that generation. A batch of at most 100 changed entries commits together initially; large imports create drafts in chunks and use an explicitly reviewed publication plan.
Two concurrent releases with the same base generation cannot both silently win. The second must rebase or conflict. Reference validation requires the intended published version of dependencies; no public entry may embed an unpublished private revision.
From commit to evidence
A worker computes affected content/listing tags, requests a bounded purge and runs the configured destination verification. Evidence includes release generation, response hash or marker, observation location, timestamp and errors. Website adapters also observe a deployed page marker; a fresh CMS API response does not prove a statically generated page rebuilt.
A failed destination never rolls back already committed content automatically. Show partial success and offer an authorized retry or reconciliation. Retry the same desired generation; discard or supersede obsolete tasks so an old worker cannot overwrite a newer release.
Rollback, unpublish and scheduling
Rollback creates a new, higher generation referencing selected older revisions after current validation. Do not decrement generations or undo orders. Unpublish creates a tombstone and a cache-removal job; retain audit and report unresolved removal paths. Historical public URLs require the revocation rules in section 15.
Scheduled release jobs persist intended time in UTC and revalidate authorization, revisions and dependencies when due. A missed schedule after downtime appears as delayed, not falsely on-time. Delivery checks are scoped observations, never a claim of universal global verification.
15 / Edge delivery and Redis
Three layers, three responsibilities
Layer
Data and contract
PostgreSQL
Authoritative revisions, publication generation, permissions, tombstones, jobs and commerce state.
Redis
Disposable, generation-keyed public content/query results; bounded TTL and memory. It is not the durable queue or correctness lock.
CDN
Approved public content/asset responses. Private/editorial requests bypass shared caching.

Cache keys and defaults
Include project, environment, recovery epoch, release generation, locale, schema/render version, normalized query and response representation. Restore changes the epoch and invalidates old live-discovery responses before serving; generations from different epochs are never interchangeable. Do not cache arbitrary unbounded query variants. Resolve the active generation from PostgreSQL on an origin miss; do not let a stale Redis pointer reintroduce an older publication.
Proposed defaults: active-release metadata and live public queries have CDN shared TTL 30 seconds; generation-pinned public content 300 seconds; Redis public results 300 seconds with jitter. Browser freshness is zero with revalidation for content. These are policies to test, not a global 30-second consistency guarantee. Disable stale-on-error for content removal paths and never serve unauthorized data as a fallback.
Signed preview, drafts, sessions, customer details, carts, checkout, order status and personalized responses use private/no-store behavior. Reject cache-key ambiguity and do not vary private data merely by a client-supplied header.
Invalidation and dependencies
Tag entry, collection, locale and known references. Include collection/listing dependencies even when a newly matching entry was absent from the old result. Begin conservatively with collection-level invalidation; optimize only after correctness tests. Cloudflare supports tag-based purging, subject to documented limits. A successful purge response and sampled reads remain different evidence. [R12]
In-flight stale fills and multiple cache layers are explicit test cases. Generation keys prevent old content from poisoning a new-generation cache; TTL and targeted invalidation govern live generation discovery. The site adapter tracks its own Next.js/Astro/Svelte build or cache layer separately.
Failure and removal policy
A Redis outage bypasses to bounded PostgreSQL reads with request coalescing and admission limits, not unlimited database load. Cache misses must not trigger unbounded parallel regeneration. Redis replication is not our durable-write guarantee. [R11]
Unpublishing marks the entry revoked for origin access, including historical generation URLs, then purges all known paths and derivatives. Report removal pending until configured checks pass; cached browser copies or previously downloaded public content cannot be recalled. Do not publish confidential material. A truly immediate revocation requirement needs an online authorization path and no shared public cache.
16 / Durable work and integrations
The PostgreSQL outbox is the delivery backbone
Store publication changes and outgoing events in the same database transaction. Worker notifications may be accelerated with Redis, but workers can discover all pending work from PostgreSQL after Redis loss or process restart.
Claim bounded batches with database row locks and leases. Record attempt generation, deadline, next attempt, status and a stable business idempotency key. A worker may finalize only its current lease/generation. Do not hold database locks across external calls. Renew a lease only while work is progressing and within the job deadline.
Delivery contract
At-least-once attempts with finite retries. The default external attempt deadline is 10 seconds; at most five attempts, with capped backoff and jitter, within a one-hour job lifetime. Adapter-specific policies may be stricter. Retry transient network errors, selected 5xx and throttling; respect bounded Retry-After. Authentication and invalid configuration errors are terminal until corrected.
An external action may succeed before its response is lost. Reconcile uncertain outcomes using release IDs, provider operation IDs or read-back evidence before repeating non-idempotent work. A local transaction cannot promise exactly-once effects in another service.
Resource and ordering controls
Start with eight worker slots, no more than two per destination and one active publication stream per project/environment. Separate AI, publishing, image and commerce concurrency pools so expensive tasks cannot starve editorial saves. Apply queue admission limits and return a clear capacity error before accepting work that cannot be retained.
Use stable event IDs and sequence/generation numbers for webhooks. Sign a timestamp and raw body, document verification and replay protection, rotate secrets, and deduplicate incoming events. Do not execute webhook-provided commands. Retain superseded delivery history but never dispatch an obsolete “make release X current” after release Y.
Failure visibility
Each job exposes pending/running/retrying/succeeded/failed/uncertain/cancelled/superseded states, sanitized evidence and a repair action. Cancellation stops new work; it does not reverse remote side effects. Manual retries remain permissioned and audited.
First integration: the direct public content API plus a reference Svelte blog. Second integration: one framework-specific website adapter with release markers and retry/reconciliation tests. Cloudflare or Vercel credentials stay server-side and narrowly scoped. No GitHub/Vercel connection is required just to edit content.
17 / AI assistance and agents at scale
AI proposes; the platform enforces
Expose a small tool set: discover schemas, query permitted content, create a draft, propose a changeset, validate, request review and inspect release status. The Rust CLI supplies these contracts through JSON. The complete system also includes an MCP adapter using the same authority rules; tool metadata never grants permission. Implement the CLI/API contract before its protocol adapter. [R36]
Nontechnical AI workflow
An editor describes a goal, selects source material and receives a structured draft or diff. Show which sources were supplied, which claims are unsupported, and what changed. Accepting a suggestion creates a normal revision. The AI must not invent client testimonials, prices, legal promises or measured business outcomes.
Provide AI assistance as an optional module; manual editing must work when the model provider is down. Keep model keys on the server. Use a provider abstraction and record provider/model, prompt version, execution ID, tokens and estimated cost. Actual billing reconciliation is separate from estimates.
Bounded agent operations
Default service-account authority is draft-only. Enforce per-project request, token, cost, document and concurrency budgets. Bulk changes use a manifest of exact IDs/base revisions; initial chunks contain at most 100 records and 1 MiB of input. Return per-item outcomes and a resumable cursor. Do not pretend a multi-chunk operation is globally atomic.
Authorize and reserve conservative per-request cost/token allowances in PostgreSQL before dispatch. Redis counters cannot bypass the configured admission budget. Estimated provider cost is not a guarantee of the final invoice; retain uncertain reservations until reconciled and alert on rate or billing discrepancies. On ambiguous provider timeout, preserve uncertainty and reconcile where possible. A timeout may still incur provider cost.
Prompt-injection and action boundaries
Treat retrieved content, media text and instructions inside documents as untrusted data. Do not allow content to modify system instructions, permissions, network destinations or secrets. Model output must match a validated typed action; recheck actor scope and approval before execution. Least privilege and review are part of the threat model, not a complete prompt-injection solution. [R15]
Evaluation suite
Maintain a versioned test set covering schema discovery, correct edits, missing facts, malicious instructions, stale revisions, cross-project access, bulk interruption and provider failures. Measure schema-valid output, task completion, unauthorized attempts, reviewer edit effort, latency and cost. Required gate: no unauthorized action executes; quality targets are set from human-reviewed baselines. Run repeated trials and record model versions rather than choosing a favorable single result.
Autonomous publishing is opt-in, restricted to specific collections/actions/budgets and revocable. Production schema changes, refunds, credential changes and role escalation remain separate high-risk permissions.

20 / Commerce catalog, carts and checkout
One merchant per store; content and money remain distinct
The full commerce scope includes digital and physical products, product variants, stock reservations, shipping rules, tax configuration, one-time purchases, subscriptions, order management, refunds and entitlements. A merchant is associated with one Stripe account per environment. Marketplace payouts, split sellers and replacing a financial accounting system are outside this product.
Product and price data
A product has editorial descriptions plus separately permissioned commercial records. Variants own SKU, option values, delivery type, weight/dimensions if required, stock policy and active price records. Store money as integer minor units plus currency and use currency-specific validation. Prices are immutable records: changing a price creates a new record, not a rewrite of historic orders.
Support explicitly configured currencies, one currency per cart, and separate checkout paths for recurring and one-time purchases. Mixed recurring/one-time carts are rejected with a clear message. A normal content editor or writing agent may change descriptions but cannot grant a discount, change price, alter stock or issue a refund without those specific permissions.
Checkout lifecycle
	•	The browser sends product/variant IDs, quantities, chosen currency, promotion code and permitted delivery selection. It never supplies an authoritative payable total.
	•	Rust validates the current sellable catalog, quotas, allowed destination and eligible price. It creates an immutable quote revision and pending order, reserves relevant stock and discount capacity, and records a durable payment intent to create Checkout.
	•	The worker creates a Stripe-hosted session using a stable business operation key, approved line items and shipping/tax settings. A lost response enters reconciliation; a second request must not blindly create another charge path.
	•	The customer pays in the hosted interface. Shipping/address-dependent tax may be finalized there; reconcile resulting line items, discounts, shipping choice, currency and tax calculation against the authorized quote policy before confirming the final order snapshot.
	•	A verified provider event and authoritative reconciliation update payment state. The redirect page only displays progress. Fulfillment is independently queued after the committed paid transition.
Customer and order records
Customer access uses an authenticated account or a high-entropy scoped order capability; an order number is not a credential. Public catalog, private order, payment, fulfillment and refund models are separate. Historical order lines snapshot description, price, tax, discounts, currency and delivery promise. Product edits never recalculate a completed purchase.
Enablement checks
The Studio provides a setup wizard for merchant identity, test/live credentials, webhook secret, prices/currency, refund policy, tax mode, allowed destinations and transactional messages. It performs test Checkout and callback reconciliation before enabling selling. A key alone never turns an unfinished integration live. Each optional capability is enabled only after its acceptance gate passes.
21 / Inventory, shipping and tax
Deterministic stock allocation under concurrent purchase
Keep an append-only inventory movement ledger and transactionally maintained SKU/location balances in PostgreSQL. Track on_hand, reserved and allocated; available stock is on_hand - reserved - allocated. Never trust a Redis count or a storefront badge when accepting an order.
Reserve every cart line in one short transaction with sorted SKU locks and conditional capacity checks. If any line lacks stock, roll back the reservation. A paid order converts its reservation to allocation; shipping reduces on-hand and allocation together. Cancellation releases a reservation/allocation according to fulfillment state. Restocking requires an explicit received-and-inspected return movement, not merely a refund event.
Expiry and uncertain payment
The reservation expiry is aligned with the Checkout session's recorded expiry plus a reconciliation grace period. Before releasing an expired reservation, inspect provider state and attempt to close an unpaid session where supported. If the provider is unavailable, mark uncertain and extend only within a bounded hold policy; surface manual action instead of infinite holds.
A late paid result after stock was released must reacquire stock transactionally. If insufficient, the order becomes paid_unfulfillable, fulfillment is blocked and an authorized compensation/refund workflow starts. Never silently oversell or label a captured payment failed. Delayed payment methods for stock-limited items remain disabled unless this complete hold/late-success policy is exercised in tests.
Shipping contract
Operators configure allowed countries/regions, rate tables, pickup, free-shipping thresholds and delivery estimates. Quote rules include currency, tax treatment and validity. Start with configured rates and manually entered carrier tracking; an external rate adapter uses the same bounded quote contract. Address changes invalidate prior eligibility/quotes. Carrier purchase/label calls require idempotency or reconciliation before repeating.
Fulfillment supports partial shipments per line, tracking events, cancellation before dispatch and return requests. Never infer physical delivery from payment success. Unknown carrier state remains unknown. A shipping notification fails independently of order/stock commits.
Tax contract
Use the configured Stripe Tax integration or an explicitly approved merchant rate adapter; do not implement worldwide tax-law inference in an LLM. Product tax codes, inclusive/exclusive price behavior, customer location and registration settings are explicit. Stripe's Checkout tax integration uses configured registrations and customer address data. [R33]
Capture provider calculation references and amounts on the final order. If required location data, configuration or the tax calculation is unavailable, block checkout for that destination rather than charging zero silently. Tax-disabled mode is a merchant-approved configuration with an audit record, not a legal conclusion. Registration, filing, invoicing and local obligations require merchant review before enabling a region; the CMS does not promise universal compliance.
Acceptance: concurrent last-item purchases, expired sessions, provider outage, late payment, partial shipping, returned stock, currency mismatch and changed shipping address are mandatory fixtures.

Make every uncertain external effect inspectable
Stripe calls use a server-side adapter with a pinned provider API contract. Credentials are project/environment-scoped and stored as encrypted secret references. The event endpoint verifies raw-body signatures and timestamp tolerance before processing; it acknowledges only after a unique provider-event receipt is committed. Delivery retries and event reordering are expected. [R13]

Per-entity sequence; suppress or summarize obsolete queued messages instead of sending misleading current-state claims.
Content
Deterministic escaped templates, no header injection; secret-free errors and no broad administrator links in public email.

User experience and tests
The operator sees pending, sent, retrying, failed, suppressed and uncertain delivery. Delivery acceptance does not prove a human read the message. A channel test never creates a real order or publishes content. Templates include new lead, review requested, publication delayed, order confirmation, shipment and subscription status notices.
Test a successful saved submission while email is down, repeated browser submission, escaped malicious content, exhausted queue, revoked CRM key, reordered delivery and project deletion. New leads are rejected before acceptance if durable capacity is unavailable; the interface preserves the entered form locally long enough to explain retry without claiming it was submitted.
25 / Integration, deployment and domain contracts
Every adapter reports what it can actually confirm
The integration contract is validate_configuration, plan, execute, inspect, reconcile and revoke. A plan contains project, environment, generation, input digest, permissions, destinations and an execution budget. Adapter output separates request accepted, provider completed and observed result. Capabilities are advertised explicitly; lack of readback produces uncertain status rather than invented confirmation.
Direct edge API and generated websites
Direct consumers pin one generation across related reads. Generated websites build from a release manifest and include a machine-readable generation marker. Each deployment attempt records the source commit, schema/renderer hashes, CMS generation, provider deployment ID and eventual serving URL. Verify the marker after promotion; updating the CMS does not establish that a site has rebuilt.
Serialize desired deployment promotion per destination. Stale workers may finish a build but cannot promote a generation older than the current desired one. Cancellation disables further promotion; if the provider already promoted, reconcile and either keep it or issue a new authorized rollback deployment. Never overwrite customer commits or force-push to a repository from an unreviewed agent task.
GitHub and hosting integration
Use a narrowly scoped repository application/token and an explicit branch policy. The installer previews files before creating a starter; writes go through a branch/PR unless the owner expressly authorizes direct delivery. Hosting adapters cover a static deployment artifact and one tested Vercel integration; other hosts implement the same interface. Infrastructure credentials stay server-side and separately revocable. Deployment webhooks use signed receipts and durable deduplication.
Custom domains and origin binding
Require domain ownership proof before routing a host to a project. Store canonical hostnames and environments; reject unknown Host values and do not derive tenant identity from untrusted forwarded headers. DNS/certificate provisioning is an asynchronous job with pending/ready/failed states. Cache namespace and TLS routing change together through a reviewed plan. Release a domain only after routes, certificates, caches and ownership tokens are removed, avoiding stale tenant mappings.
Extension packaging
First-party modules are compiled Rust components or isolated trusted workers with declared capabilities. A manifest declares core compatibility, schemas/migrations, permissions, events, health checks, resource budgets and uninstall policy. No arbitrary downloaded native code runs inside the privileged API process. Future external plugins must use an isolated, authenticated API/worker boundary; they do not receive production database credentials.
Acceptance: expired credentials, lost deployment response, out-of-order builds, deleted branch, wrong domain proof, stale webhook, failed CDN purge, partial asset upload and adapter upgrade all produce observable states and a safe next action. A client must remain able to edit/export while a hosting integration is unavailable.
26 / Security requirements
A threat model, not a blanket security promise
Map requirements and evidence to OWASP ASVS 5.0, targeting the relevant Level 2 controls before a public production release. Document exclusions and independent review; this document is not a certification. [R18]

Required control and proof

Object/field authorization plus database constraints/RLS. Negative tests for APIs, workers, export, search and caches.

Conservative starting limits
API bodies: 1 MiB, except separately streamed uploads. Rich-text depth: 16; relation expansion depth: 2. Query page maximum: 100. Database query deadline: 2 seconds for normal reads, with explicit longer budgets only for administrative jobs. API pool: 20 connections; worker pool: 10 on the reference profile. These are initial bounds to tune from evidence.
Run as non-root, use read-only application filesystems where possible, restrict outbound destinations and do not publish database/Redis ports. Separate administration and public delivery credentials. Limit both structured application logs and container stdout retention. Safe Rust does not prevent authorization, logic, dependency or denial-of-service bugs.

Retention baseline
Keep live content and revisions pinned by active releases. 32 / Deployment, observability and recovery
Local simplicity; explicit production topology
Local Compose runs PostgreSQL, Redis, a test object store and a reference identity-provider profile beside Rust API/worker and Svelte development servers. Production serves compiled Svelte assets, Rust services and private infrastructure. Use an external TLS proxy/CDN, non-root containers, resource limits and persistent managed or self-hosted storage. Kubernetes is not required for the first installation.
Operational signals
Correlate request_id, project, actor, revision, release, job, destination and deployment version. Expose HTTP error/latency, save conflicts, publish lag, queue age, failed/uncertain deliveries, cache hit ratio, database pools/locks, WAL size, Redis memory/eviction, model budget consumption and dropped logs. Export optional OpenTelemetry-compatible traces; public logs never reveal draft text or credentials. [R25]
/livez means process responsiveness. /readyz reports whether this role can safely serve its required operations; Redis failure can be degraded rather than universally unready if bounded fallback is available. Database failure makes writes unavailable. Check the status page and service health from another failure domain. Service Monitor can supply that external view but is not the only way to deploy the CMS.
Data protection and objectives
Use encrypted daily base backups and continuous PostgreSQL WAL archiving for a proposed 15-minute recovery-point objective and one-hour recovery-time objective on the reference profile. Both require demonstrated restore drills. PostgreSQL documents PITR mechanics; a SQL dump alone is not that strategy. [R24]
Version object-store assets and preserve a consistent backup manifest, schemas, migrations, encryption-key references and deletion ledger. Redis does not require restoration for correctness. Keep backup credentials separate, test access and restore on clean infrastructure, with outbound publishing/payments disabled until reconciliation.
Upgrade runbook
Read release notes and compatibility constraints → verify backup → rehearse on staging → apply additive schema → deploy compatible binaries → run smoke checks → backfill → remove old fields only after the support window. Roll back binaries only against a compatible schema. Otherwise restore or forward-fix with an explicit data-loss and reconciliation plan.
Capacity, outages and cost
Set project storage/revision/media quotas, queue caps and retention. Monitor free disk and WAL growth; reserve capacity before accepting large jobs. Keep cache reconstruction and diagnostics bounded. On provider outages, retain drafts, show pending publication and expose next actions. On a cold restart, do not replay all historic effects blindly.
Record operating cost per deployment and per 1,000 defined operations. Hosting, CDN bandwidth, object storage, email, model usage and payment fees are distinct. Do not equate low Rust memory usage with a profitable service.

The system must be maintainable without its original author
All values below are proposed defaults, configurable through validated settings and measured in staging. Budgets constrain admission; they are not guarantees that arbitrary traffic fits a fixed machine. Monitoring and recovery operate independently of the production application where possible.
Resource
Default guard and behavior
HTTP API
1 MiB JSON input, page size at most 100, 2-second ordinary query budget; 429/503 before unbounded queues form.
Jobs
10,000 pending jobs/project and 1 GiB pending payload metadata/installation; stop accepting new expensive work before reserves are exhausted. Large bodies live in referenced object storage.

Failure runbooks
PostgreSQL unavailable: fail writes honestly, stop accepting durable jobs, keep only eligible previously public cache data within TTL, and publish role-specific degraded status. Restore connectivity and verify migrations/recovery before admitting traffic. Never acknowledge a write based on a local queue.
Redis unavailable: disable the failed cache path, coalesce identical public reads and cap database fallback. Authorization, mutations and budget reservations continue through PostgreSQL if capacity permits. Rebuild keys gradually; never flush unrelated namespaces or replay business jobs because cache data vanished.
Publishing/CDN backlog: inspect oldest due work, provider rate limits, generations and credentials. Retry only the current desired generation, coalesce obsolete work, and keep pending/uncertain evidence. Do not purge the entire zone as an automatic response to one failed update.
Suspected credential leak: revoke the affected scoped principal, rotate related secrets, pause its new actions and preserve audit evidence. Investigate actions already executed; do not claim revocation undid external effects. Follow the private security-report process before public disclosure.
Disk pressure or damaged storage: stop unsafe admission, preserve diagnostics and snapshots, and apply measured retention. Never delete database WAL or unfulfilled order state to create free space. Restore to a clean environment when needed; record the data gap and reconcile external effects.
Restore and deletion ledger
Keep an access-controlled off-host deletion ledger and backup manifest so post-backup deletions can be reapplied. Recovery is blocked from public serving if the required ledger interval cannot be reconstructed. Restore with outbound integrations disabled, verify schema/assets/permissions, assign a new recovery epoch, reconcile provider effects, and explicitly enable current jobs. A backup existing is not proof of a working restore.

A human authors a localized article; an agent proposes a constrained edit; a reviewer approves the exact diff; publishing commits and updates a real site; a delayed cache is visible and safely reconciled. The same workflow can be inspected from Studio and CLI.
A customer submits a lead while mail is unavailable; the lead survives and notifications recover. A customer buys the last physical item under concurrent demand; the order, stock and payment remain consistent. Digital fulfillment is deduplicated, a partial refund reconciles, and a subscription cancellation expires access on the configured boundary.
An operator upgrades and restores onto clean infrastructure, reapplies deletions, reconciles external actions and resumes service without accidentally publishing, charging or notifying twice. The measured deployment withstands the documented load and failure scenarios with known limits disclosed.
Definition of ready to build versus ready to rely on
The specification is ready to guide implementation. Production reliance requires executed evidence, dependency locks, configured providers/regions, a completed security review appropriate to exposure and a tested support/restore process. These are acceptance gates for the defined design—not missing product specifications or promises that tests have already run.
37 / End-state, moat and launch decision
What a complete product means
A developer installs a documented, versioned release. A business editor creates and previews an article, receives a reviewable AI suggestion and publishes it. The CMS records the release, updates appropriate public caches, shows destination evidence and preserves a safe recovery route. An agent can perform the same permitted operations at bounded scale through stable contracts. A maintainer can upgrade, back up, restore and diagnose the installation without relying on its original author.
Commerce and other templates extend that foundation through tested modules; they do not redefine the correctness of content, authentication or publishing. The platform remains useful without AI and without our experimental runtime.

Treat each as a hypothesis. Rust, Redis, a CDN, a CLI and templates are not individually a moat. Do not frame existing CMS products as lacking features they already document. Compare the end-to-end job under realistic failures and count maintenance cost, not just happy-path speed. [R27–R29]
Pilot and release gates
Begin with one authorized internal noncritical content site. Then recruit three independent developer/editor pairs. Measure time to first useful preview, first successful publication, failure diagnosis, recovery, ongoing edits and willingness to keep using the system. Publish anonymized findings only with consent.
Declare the defined product ready only when enabled modules satisfy their requirements matrix, load results are reproducible, limitations are visible, a clean restore works, and independent developers/editors can install, use and upgrade from the docs. Require an independent security review before production commerce or broad public exposure; testing this document is not that review.
Deployment parameters and validation evidence
The fixed architecture still needs an executable dependency lock, configured OIDC issuer, object-store bucket, CDN account/limits, merchant credentials, allowed shipping/tax regions and owner license approval. These are installation and validation inputs, not missing feature definitions. Deployment checks block capabilities with incomplete prerequisites rather than inventing account details, legal conclusions or capacity results.
First CMS implementation task: prove one Svelte editor can save a validated PostgreSQL draft through Rust, with the CLI creating the same record, a deliberate conflict returning safely, and another project denied access. Then build publishing. This is the first useful slice—not a full CMS clone on day one.

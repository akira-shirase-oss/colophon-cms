# Decisions and deviations from the master spec

The master spec ([spec/](spec/README.md)) remains the reference design. This file records every place where Colophon
deliberately differs from it, plus decisions that are still open. Add an entry whenever a design changes: date,
decision, reason, impact.

## Made

| ID | Date | Decision | Reason | Impact |
|---|---|---|---|---|
| D-001 | 2026-10-25 | The project is named **Colophon CMS**. | A book's colophon records how, when and by whom it was printed: proof of what was published. | Crates are `colophon-*`; the CLI binary is `colophon`; the reference site has a `/colophon` page. |
| D-002 | 2026-10-25 | The goal is an open-source and portfolio project that is genuinely useful. Selling is out of scope. | The maintainer's stated goal ([WHY.md](WHY.md)). | Scope is judged by proof and usefulness, not market fit or feature count. |
| D-003 | 2026-10-25 | **Proof over breadth**: four signature features (crash-proof publishing, deterministic simulation, time travel, delivery receipts) define the product. | Hard-to-fake evidence is what makes the project stand out ([WHY.md](WHY.md)). | Time travel and delivery receipts, already supported by the spec's data model (§07, §14), become first-class, user-visible features. |
| D-004 | 2026-10-25 | The spec's `ai` crate becomes **`colophon-automation`**. The AI writing assistant is optional, off by default, and built last. | "Not another AI jargon" project. Scoped automation for scripts and agents is the useful part. | [modules/09-automation.md](modules/09-automation.md). |
| D-005 | 2026-10-25 | New module **`colophon-sim`**: deterministic simulation harness, real-process crash loop, consistency checker. | The spec requires fault tests (§30); Colophon makes them a signature feature. | Domain logic must stay I/O-free and driveable by a virtual clock ([modules/10-sim.md](modules/10-sim.md)). |
| D-006 | 2026-10-25 | **Parked:** commerce, payments, inventory, shipping, tax, refunds, subscriptions, entitlements (§20–23); hosting adapters and custom domains (§25); membership and knowledge-base templates (§19). **Later:** forms and leads (§24), source import adapters (§12), full localization UI, schema designer. | Each is a large product surface that adds breadth, not proof. | Spec milestone M6 is out of v0.1. Parked areas keep their spec contracts for a future return ([modules/parked.md](modules/parked.md)). |
| D-007 | 2026-10-25 | Requirement owners in spec §36 are mapped onto real crates: `cache` → delivery, `policy` → auth, `templates` → web/blog template, `forms` → parked. | §36 names modules that the §03 repository layout does not define. | Module docs are the single owner map. |
| D-008 | 2026-10-25 | The CLI command lists in spec §09 and §11 are merged into one contract. `module enable` is dropped (no optional modules in v0.1). Time-travel commands are added. | The spec lists two slightly different command sets. | [modules/08-cli.md](modules/08-cli.md) is the only command reference. |
| D-009 | 2026-10-25 | Duplicate template material in spec §18 and §19 is consolidated into one blog template doc. | Avoid drift between two definitions. | [modules/15-web-blog.md](modules/15-web-blog.md). |
| D-010 | 2026-10-25 | Planning assumes ~45 hours/week. | The maintainer offered 8–16 hours/day; some gates depend on people and calendar time, not hours. | Estimates in [ROADMAP.md](ROADMAP.md). |
| D-011 | 2026-10-25 | The Studio uses **Material Design 3** as its design language: colour roles generated with `@material/material-color-utilities` from a brand seed, the M3 type scale, shape, elevation, state layers and motion, exposed as CSS custom properties and Tailwind theme tokens in `packages/ui`. Components are built on **Bits UI** headless primitives (keyboard and screen-reader behaviour), styled to the M3 specs. | The maintainer asked for M3. It is a complete, documented, accessible design system, and a token-first implementation keeps the components owned and Svelte-native. Not adopted: `@material/web`, Google's M3 web components, whose README says it is in maintenance mode pending new maintainers (checked 2026-10-25); MUI, which is React-only. | Replaces spec §02's "shadcn-svelte" styling; Tailwind and Bits UI stay. See [modules/14-ui.md](modules/14-ui.md) and [modules/11-studio.md](modules/11-studio.md). The public blog keeps its own look and may share tokens. |
| D-012 | 2026-10-25 | The logo is the octagonal C mark with the "Colophon CMS" wordmark. | Shared by the maintainer. | [brand/](brand/README.md); the SVG there is a recreation until the original files are added. |
| D-013 | 2026-10-25 | The toolchain is pinned to **Rust 1.99.1** in `rust-toolchain.toml` (clippy, rustfmt, minimal profile), with `rust-version = "1.99"` and edition 2024. `scripts/check-toolchain.sh` fails whenever the `rustc`/`cargo` on `PATH` differ from the pin. | 1.99.1 was the latest stable (rust-mastery, checked 2026-10-22). On the maintainer's machine Homebrew's `cargo` 1.96.0 comes first on `PATH` and ignores `rust-toolchain.toml`; the check turns that silent mismatch into a loud failure. | Run Cargo with rustup's proxies first on `PATH` (`export PATH="$(brew --prefix rustup)/bin:$PATH"`). Removing Homebrew Rust machine-wide is left to the maintainer. Closes O-001. |
| D-014 | 2026-10-25 | One local entry point, `scripts/check.sh`, runs exactly what CI runs: toolchain, `cargo fmt --check`, Clippy with `-D warnings`, tests, docs with `-D warnings`, the architecture rule, and `cargo deny`. CI pins every third-party action to a commit SHA. | "It passed on my machine" should mean "it will pass in CI" (spec §34, §35). | `.github/workflows/ci.yml` also runs daily for new advisories. Since step 0.3, when the local stack is up, `scripts/check.sh` also runs CI's integration half: the stack checks, the tests that stop stack services, the testbed in Chromium and a 200,000-request load smoke run (`QUICK=1` skips them). |
| D-015 | 2026-10-25 | The cache is **Valkey** (9.0.6 locally), run as a disposable, bounded store: no snapshots, no append-only file, `maxmemory 128mb` with `allkeys-lru` eviction, and a password. Colophon still talks to it through a Redis-protocol adapter. | Redis 8 is licensed AGPLv3/RSALv2/SSPLv1 (spec §35); Valkey is the BSD-licensed, protocol-compatible fork under the Linux Foundation. Making the cache unable to keep anything turns "disposable" from a promise into a property. | Closes O-002. Compatibility with Redis itself is a cache-adapter contract test (P3). `scripts/stack.sh check` fails if the cache is ever configured to persist or to grow without limit. |
| D-016 | 2026-10-25 | Local object storage is **Garage** (2.5.0, single-node mode), replacing the spec's MinIO. Colophon uses only the S3 API, never Garage-specific features. | MinIO stopped publishing community images in October 2025 and was later archived; its Docker Hub repository no longer exists (checked 2026-10-25). **RustFS** (Apache-2.0) was rejected for its 2026 advisory record, which includes a presigned-POST policy bypass (CVE-2026-27607) and a multipart-copy authorization flaw (CVE-2026-39360), the exact paths Colophon's uploads rely on. **SeaweedFS** has more moving parts (masters, volumes, filers). Garage is a single Rust binary used in production. Its AGPL-3.0 licence does not reach Colophon, which neither ships nor modifies it. | Garage implements presigned URLs, POST uploads, multipart, copy, CORS and expiry rules. It lacks bucket versioning, object lock, and bucket policies and ACLs (its compatibility reference, checked 2026-10-25). So locally, public and private objects use separate buckets, and versioned asset backups (module 18) are verified against the production store at P6. The media contract tests (P4) decide compatibility with other stores. |
| D-017 | 2026-10-25 | **The local stack** is `deploy/compose.yaml`: PostgreSQL 18.6, Valkey 9.0.6, Garage 2.5.0 and Keycloak 26.8.1, each image pinned by tag and digest. Every port is bound to `127.0.0.1` and the bind address is not a setting. Host ports: 55432, 56379, 53900/53903 and 58080, each movable with a `COLOPHON_*_PORT` variable. `colophon-server`'s development address is `http://localhost:58000`, the exact redirect URI in the development realm. `scripts/stack.sh up` starts the stack and runs its checks; CI does the same from a clean clone. | A container healthcheck only proves that a container answered its own probe. The checks use each service the way `colophon-server` will, through its published port, and make every service refuse something: a wrong password, an anonymous read, a corrupted upload, a reused sign-in code, a sign-in without PKCE. Fixed local binding keeps the public development credentials from ever being reachable from the network (O-008). | Keycloak runs in development mode with the `colophon` realm imported on each fresh start; the realm allows only the Authorization Code flow with PKCE S256 and has no password grant. Readiness reporting moves into Rust with `colophon doctor` and `/readyz` (step 0.3); the script stays as the outside-in check. |
| D-018 | 2026-10-25 | **Every feature is regression-tested, exercised through a separate testbed frontend, and load-tested.** (1) Rust unit tests, in-process API tests and black-box tests against the real binary and the local stack run in CI on every push; every fixed bug gets a test that fails without the fix. (2) `apps/testbed`, a SvelteKit app separate from the Studio, uses each feature through the real HTTP API, and Playwright runs it in CI. (3) Every feature that serves requests gets a k6 scenario with thresholds. A full run sends at least 1,000,000 requests; its summary, machine and commit are committed under `perf/results/`, and a run that misses a threshold or regresses past the baseline tolerance fails. | The maintainer's rule (2026-10-25): the system has to handle millions of requests, and features must stay proven as the code grows. | Laptop numbers are evidence about the code, not a capacity promise for production hardware, so every result names the machine it ran on. CI runs a shorter load smoke test with absolute thresholds, because shared runners are noisy; million-request runs happen locally and at every milestone gate. |
| D-019 | 2026-10-25 | **Ownership** (closes O-009): Claude builds every crate and app, `colophon-db` included, and the maintainer reviews. Changes to database migrations, authentication, publishing transitions and provider adapters are listed in that step's build-log entry for line-by-line review (spec §34). | The maintainer chose to keep building at full pace ("continue and keep building and committing"). | Supersedes the proposed split in `AGENTS.md`. |
| D-020 | 2026-10-25 | **One JavaScript package manager: npm**, with workspaces declared in the root `package.json` (`apps/*` now; `packages/*` later) and one committed `package-lock.json`. Exact versions in each app's `package.json`. | Ships with Node, so contributors and CI need nothing extra; workspaces cover the planned Studio, UI kit and SDK. | Partly closes O-007: the Studio's server-state library is still open. Reconsider pnpm if dependency isolation becomes a problem. npm's install-script approval stays off for every package: the only one asking is `fsevents`, an optional, prebuilt macOS file watcher. |
| D-021 | 2026-10-25 | **The rich-text format is `colophon/rich-text` v1** ([formats/rich-text-v1.md](formats/rich-text-v1.md)): paragraphs, headings 2–4, bullet and ordered lists, quotes, code blocks, horizontal rules, line breaks, media-library images (an asset id and required alt text, never a URL) and one custom block, the callout (note, tip, warning); marks bold, italic, strike, code and link (https, http, mailto, `/paths`, `#fragments`). Depth 16, 256 KiB, 10,000 nodes. A canonical form, and error codes with JSON Pointers. | A blog-shaped set that every renderer can draw safely, small enough to prove completely. The shared fixtures (12 valid, 30 invalid) are the contract between the editor, the Rust validator and the renderer. | Settles module 12's open "v0.1 block set" question. Tables, embeds and footnotes can come in a v2 with its own fixtures; stored v1 documents stay valid. |
| D-022 | 2026-10-25 | **The editor opens a document only if it can reproduce it byte for byte.** After loading, it converts the document back and compares it with what was stored; any difference and the document is refused, with the JSON Pointer of the first difference. Tiptap's trailing-paragraph feature is off, so an edit changes only what was edited. | ProseMirror silently drops what its schema can't hold, including unknown fields and attributes that Tiptap's content check doesn't report: 7 of the 30 invalid fixtures would have been changed on save without this check. "Data is never dropped silently" (module 01) has to hold in the editor too. | The server-side validator (step 0.5) is still the authority; documents written through the API in a non-canonical form must be canonicalized or rejected there. |
| D-023 | 2026-10-25 | **One renderer implementation.** `renderToHtml` builds every tag itself and escapes every piece of text; the `RichText` Svelte component is a thin `{@html}` wrapper around it, so the Studio preview and the public site can't drift (R1). It is strict: anything outside the format throws `UnrenderableContent` rather than being guessed at. Only the Studio, which previews drafts the server hasn't judged yet, passes a fallback that explains the refusal. | Two implementations (Svelte components and a string renderer, as module 12 first described) would need their own agreement tests and could still drift. The output uses no inline styles or scripts, so it works under a strict Content Security Policy. | Reviewed expected output for every valid fixture lives in `fixtures/rich-text/v1/rendered/`; the Studio's preview is checked against it as a DOM. Element and attribute allowlist: p, h2–h4, ul, ol (start), li, blockquote, pre, code (class), hr, figure, img (src, alt, loading, decoding), aside (class, role), strong, em, s, a (href, rel), br. |
| D-024 | 2026-10-25 | **The brand seed is `#2f5bd3`** (closes O-016), in `packages/ui/theme.json`, with Material's **fidelity** scheme, so the primary container is exactly the seed. A custom success role (for "Verified at configured locations") is harmonized toward the seed with chroma capped at 40. Six schemes: light and dark at standard, medium and high contrast; `data-theme` and `data-contrast` on `<html>`, defaulting to the system's. | The deep blue the Studio already used; the maintainer asked to keep moving rather than stop for a choice. The default tonal-spot scheme muted it to `#4c5c92`. CI checks that every role and its `on-*` pair keep WCAG AA (4.5:1) at standard and medium contrast and AAA (7:1) at high contrast: 116 checks, tightest margin 4.53:1. | Change the seed in one line and run `npm run generate -w @colophon/ui`; CI fails if `tokens.css` is stale or contrast drops. `@material/material-color-utilities` is pinned to 0.3.0: 0.4.0 imports `./dynamic_color` without an extension, which Node refuses to load. |
| D-025 | 2026-10-25 | **Components are built on Bits UI and styled with scoped Svelte CSS over the M3 tokens** (closes O-015): toolbar (one tab stop, arrow keys), tabs, dialog (focus trap, Escape, focus return), dropdown menu, buttons, text fields, top app bar. `m3-svelte` is not adopted. Tailwind is deferred until utility classes pay for themselves. Typeface: Roboto Flex, self-hosted through `@fontsource-variable/roboto-flex`, so the Studio makes no request to anyone else's servers. | Bits UI supplies the keyboard and ARIA behaviour that is hardest to get right; owning the styles keeps components Svelte-native and token-only. `m3-svelte` has a single maintainer and a dual GPL licence. Scoped CSS covers what exists today with one less build tool. | Amends D-011 (Tailwind). Automated accessibility checks (axe, WCAG 2.1 AA) run on the Studio in four theme and contrast combinations in CI. |
| D-026 | 2026-10-25 | **SQL is checked at compile time with committed offline data** (closes O-003): `sqlx::query!` macros, the `.sqlx/` directory committed, builds use `SQLX_OFFLINE=true`, and CI's integration job runs `cargo sqlx prepare --check` against the real database. | Compile-time checking catches typos and type mismatches before tests run; offline data keeps builds working without a database. | Takes effect with the first query in P1. |
| D-027 | 2026-10-25 | **The OpenAPI document is generated with utoipa** (closes O-004) from the Rust types and handlers, exported to `docs/api/openapi.json`, committed, and diffed in CI so every API change is visible in review. | The most widely used OpenAPI crate for Axum, code-first, so the document can't drift from the code. Checked against rust-mastery chapter 15's checklist when adopted. | Takes effect with the first `/api/v1` resource in P1; the SDK (module 13) is generated from it. |
| D-028 | 2026-10-25 | **Domain ports: a synchronous, I/O-free core** (closes O-005). Rules and state machines in `colophon-domain` are plain functions over values; adapters (database, cache, clock, IDs) sit behind traits used generically inside the domain, with `dyn` chosen only at the composition root in `colophon-server`. | The rust-mastery default; it lets the deterministic simulator drive the domain with a fake clock and fake I/O, and keeps async out of the rules. | `scripts/check-architecture.sh` already keeps I/O crates out of the domain. |
| D-029 | 2026-10-25 | **Content hashes are SHA-256** (closes O-006) over canonical bytes: revisions, changesets (approval by exact hash) and ETags, written as `sha256:<hex>`. | Available everywhere, including the browser's Web Crypto, so the Studio can check the hash of the exact change a reviewer approved. BLAKE3 is faster but isn't in Web Crypto, and these inputs are small (≤ 256 KiB). | The `sha2` crate on the server. |
| D-030 | 2026-10-25 | **The Studio's server state uses TanStack Query for Svelte** (closes O-007), from the first API calls in P1: queries keyed by project, environment and resource; mutations that send the expected revision and an idempotency key, and invalidate exactly what they change. | Caching, retries with backoff, cancellation and request deduplication without fetching inside effects; it matches the save rules (expected revision, conflicts are answers, not errors). | The package manager half of O-007 is D-020. |
| D-031 | 2026-10-25 | **The OpenID Connect relying party is built on `reqwest` and `jsonwebtoken`** (closes O-008), in `colophon-auth`, not the `openidconnect` crate: discovery (the document's `issuer` must equal the configured one), the Authorization Code flow with PKCE, `state` and `nonce`, the code exchange, and ID-token verification with an asymmetric-only algorithm allowlist, exact `iss`/`aud`, `azp` when present, `exp`/`nbf` with a minute of leeway, and keys from the provider's JWKS refreshed at most once a minute. Every provider request has a timeout and a 64 KiB response limit. **The development identity** is the Keycloak realm in `deploy/keycloak`; its client secret is public, so the server refuses to start with it on a non-loopback listen address. | `openidconnect` 4.0.1 (last release 2025-07-06) depends on `rsa`, whose RUSTSEC-2023-0071 (Marvin timing attack) has no patched version (advisory database, 2026-09-12), plus a second, older crypto and encoding stack. One flow for one kind of provider is a small amount of code, and `jsonwebtoken` on `aws-lc-rs` shares the crypto library TLS already uses; `rsa` and `ring` are not in the dependency tree. | Colophon owns the verification code, so the tests must cover each attack: another key under the provider's key id, wrong or missing nonce, wrong issuer or audience, expired, not yet valid, no subject, a foreign `azp`, missing or unknown key id, HS256 signed with the public key, and `alg: none` (keys generated per run). The server's end-to-end tests sign in through the real Keycloak. Another provider is accepted once it passes the same tests. |
| D-032 | 2026-10-25 | **Sessions are server-side rows; the cookie holds only a random token.** `colophon_session` carries 256 random bits (`HttpOnly; Secure; SameSite=Lax`); Postgres stores its SHA-256 hash. A session ends 12 hours after sign-in or after 2 hours unused, and its last use is written at most once a minute. Cookie-authenticated writes need an `Origin` that exactly matches the public origin or `COLOPHON_TRUSTED_ORIGINS`, and an `X-CSRF-Token` equal to the session's CSRF token (also stored hashed; its cookie is readable and `SameSite=Strict`). A sign-in attempt is a Postgres row keyed by the SHA-256 of its `state`, holding the nonce and PKCE verifier for 10 minutes; it is bound to the browser that started it by a cookie and deleted as it is used, so it works once. | Revocation takes effect on the very next request (A4) because every request reads Postgres and nothing caches sessions; Postgres stays the only authority. Hashing means a database leak yields no usable tokens. The lifetimes close the open question in [modules/03-auth.md](modules/03-auth.md). | Every signed-in request costs a session read; the cost is measured by `perf/k6/session.js`. Logout revokes the row and keeps it for the audit trail. |
| D-033 | 2026-10-25 | **The database pool skips sqlx's ping on checkout, and a full pool answers 503.** `test_before_acquire(false)`; when no connection becomes free within the acquire timeout (2 s), the request gets 503 with `Retry-After: 1` (`DbError::Busy`, `ApiError::Busy`) and is logged at warn, never as an internal error. | The ping is a round trip on every checkout. With it, the signed-in load scenario spent its time waiting on the network: 1,485 requests/s with Postgres on one core. sqlx still pings each connection when it returns to the pool and drops broken ones, so only a connection that breaks while idle (a database restart) reaches a caller, and fails that one request. Nothing reaches the database when the pool is full, so retrying is always safe. | After a database restart, up to one request per idle connection can fail. Pool size stays `COLOPHON_DB_MAX_CONNECTIONS` (16): throughput on the reference laptop grew with it (2,699/s at 16, 4,014/s at 32, 5,104/s at 64), but sizing belongs to the deployment. |

## Open (decide at the milestone shown)

| ID | Decide by | Question | Options and notes |
|---|---|---|---|
| O-010 | P2 | Worker wake-up mechanism | Polling only, Postgres `LISTEN/NOTIFY`, or Redis notifications. Workers must always be able to find all work from Postgres alone. |
| O-011 | P1 | Build the deterministic scheduler or adopt a crate | Evaluate existing deterministic-simulation crates against a small hand-written scheduler. |

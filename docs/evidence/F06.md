# F06 evidence: Collection filter gains a new matching article

Required invariant (module 17): Listing cache invalidates even though the old response did not reference the new entry.

- Origin, both directions: `crates/colophon-server/tests/delivery_query.rs` `a_filtered_listing_follows_every_release_in_and_out`. A filtered published query is cached (miss, then hit); a release adds a matching entry (it appears, a miss at the new generation) and one that never matched stays out; an entry edited out of the filter and published leaves it and appears in the other filter's answer; the answer pinned to the first generation is unchanged.
- A related entry: `query_depth.rs` `a_release_of_only_a_referenced_entry_reaches_a_populated_listing`. A cached `depth: 1` listing shows a referenced entry's new value after a release of only that entry (a miss at the new generation), and is unchanged pinned to the first.
- At the CDN: `purges.rs` `a_new_entry_reaches_a_listing_the_cdn_held_without_it`. A listing the (fake) CDN holds without a new entry is evicted by the release's purge, which names the entry's collection tag (`colophon_domain::cache::purge_tags`), and the next CDN read shows it.
- Filters and populated references exist only in the `POST …/query` document (D-107), which no CDN keeps; a GET listing never populates a reference, so no related entry can leave a CDN listing stale.

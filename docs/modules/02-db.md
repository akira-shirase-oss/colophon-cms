## Why it exists

PostgreSQL is the only source of truth. Checks in the API alone race: two requests can both pass a precheck. Uniqueness,
references, generation order and lease ownership therefore have to be enforced by the database, inside short
transactions.

## End goal

Every domain port has a Postgres implementation whose constraints back up the domain invariants. Concurrency, crash and
cross-project tests pass against a real PostgreSQL 18 container, and every migration is reviewed, forward-only and
tested on an empty database and on a fixture database.

## Responsibilities

- Migrations and the database role model.
- Tables, constraints and indexes.
- Transaction boundaries and retries.
- The outbox, inbox and idempotency storage.
- Row-level security context.
- Full-text search.
- The published projections that the delivery role reads.

## Not its job

- Deciding rules. It enforces the domain's rules; it does not invent new ones.
- External calls.
- Caching (handled by [delivery](06-delivery.md)).

## Breakdown

### Migrations (spec §12)
- SQLx migrations in reviewed SQL, forward-only.
- Large changes follow **expand → backfill → contract**.
- Steps that cannot run in a transaction (for example `CREATE INDEX CONCURRENTLY`) are marked and tested separately.
- A migration lock, statement and lock timeouts, and checkpointed backfills that can stop and resume.
- Compatibility is kept with the current and the previous application version during rolling updates.

### Tables (first cut)

| Area | Tables |
|---|---|
| Tenancy | `organizations`, `projects`, `environments` (holds `epoch` and `generation`), `memberships`, `invitations` |
| Identity | `identities` (`(issuer, subject)`), `sessions` (hashed tokens), `sign_in_attempts`, `machine_credentials` (hashed, scoped, expiring) |
| Content | `schemas` (versions + hash), `entries`, `revisions` (insert-only), `slug_claims`, `references` |
| Workflow | `changesets`, `changeset_items`, `reviews`, `comments`, `schedules` |
| Releases | `releases`, `release_items`, `publication_history` (generation intervals), `tombstones` |
| Delivery | `destinations`, `deliveries`, `delivery_evidence` |
| Work | `jobs`, `outbox`, `inbox`, `idempotency_keys`, `budget_reservations` |
| Assets | `assets`, `asset_references` |
| Governance | `audit_log` (append-only), `deletion_ledger` |

IDs are UUID v7, generated in the application (`Uuid::now_v7()`), so a row's ID is known before it is inserted
and IDs sort by creation time.

### Constraints that carry invariants
- **Composite foreign keys** over `(project_id, environment_id, id)`, so a reference can never cross a project or
  environment (D3).
- **Insert-only revisions:** no `UPDATE`/`DELETE` grants for application roles (D1).
- **Slug claims:** unique per project, environment, collection and locale, with explicit lifetimes for draft
  reservations and published routes.
- **Publication history:** candidate design is an `int8range` column with an exclusion constraint per entry and
  locale. That requires the `btree_gist` extension; the alternative is application checks under a lock (D5).
- **Idempotency:** unique `(actor, scope, operation, key)` plus a stored request hash. The result is written in the
  same transaction as the effect. Ordinary keys are kept at least 7 days.

### Transactions (spec §08)
- **Save:**
  - `UPDATE entries SET draft_revision_id = $new WHERE id = $id AND draft_revision_id = $expected`;
  - plus the revision insert, in one transaction;
  - zero rows updated → 409.
- **Release commit:**
  - lock the environment row (`SELECT … FOR UPDATE`) and check the base generation;
  - insert the release and its items;
  - close and open publication intervals;
  - advance the generation;
  - write the audit and outbox rows;
  - commit.
- **Isolation:** short READ COMMITTED transactions with explicit locks. Multi-row invariants use deterministic lock
  ordering or SERIALIZABLE, retrying **the whole transaction** at most 3 times, then returning a safe conflict or
  transient error.
- Never retry only the last statement, and never hold a transaction open across an external call.

### Outbox and leases (spec §16)
- Outbox rows are inserted in the same transaction as the change that caused them.
- Workers claim bounded batches with `FOR UPDATE SKIP LOCKED` and set lease owner, expiry and attempt generation.
- Finalizing is a conditional update on the lease owner and attempt generation (D9).

### Row-level security and roles (spec §08, §13)
- **Roles:**
  - the migration login owns the tables and runs `colophon admin migrate` (locally the stack's `colophon` user; in
    production a dedicated owner role that is not a superuser);
  - `colophon_api`, `colophon_worker` and `colophon_delivery` are privilege roles with least privilege and no login.
    Migrations grant to them; step 1.1 created `colophon_api`;
  - each process logs in as its own role that is a member of exactly one privilege role (locally `colophon_app` in
    `colophon_api`, created by `deploy/postgres/roles.sql`).
- `colophon_delivery` reads published projections only and can never read draft tables.
- Application roles never own tables and never hold `BYPASSRLS` or superuser rights. Policies use `FORCE ROW LEVEL
  SECURITY` where appropriate.
- Context is set per transaction (`set_config('app.project_id', …, true)`). Tests prove it resets correctly on pooled
  connections.
- In step 1.1, `scope::begin(pool, Scope { identity, project })` opens every project-scoped transaction. Projects,
  environments and memberships force RLS; a project is visible only inside its own context or to its members.
  Identities, sessions and sign-in attempts aren't project-scoped: the application reaches them only through
  `colophon_db::identity`, with column-level `UPDATE` grants.

### Pools and timeouts
- Pools: API 16 connections (`COLOPHON_DB_MAX_CONNECTIONS`), worker 10 (reference profile). Throughput of the
  signed-in path grows with the pool, because each connection mostly waits on round trips; size it per deployment.
- Acquire timeout 2 s; statement timeout 5 s (`PoolSettings`); explicit longer budgets only for administrative jobs.
- No ping on checkout; sqlx pings on release and drops broken connections (D-033).
- A full pool returns 503 with `Retry-After` (`DbError::Busy`), never an internal error (D-033).
- Keep round trips per request low: decide in Rust whether a write is needed (the session touch), and read what one
  response needs in one transaction (`identity::profile`).

### Search (spec §18)
- PostgreSQL full-text search (generated `tsvector` columns and GIN indexes), scoped by project, environment and locale.
- Results respect the same field and revision visibility as everything else.
- There is no separate search service until measurements justify one.

### Retention (spec §27)
- Unpinned revisions and resolved delivery metadata: 90 days.
- Terminal ordinary jobs: 30 days.
- Audit: 90 days.
- A legal hold blocks deletion for its exact scope.
- The deletion ledger is copied off-host for replay after a restore.

## Invariants enforced here

D1 (grants), D2 (conditional update), D3 (composite foreign keys), D4 (row lock plus check), D5 (exclusion constraint
or locked check), D9 (conditional finalize), plus: one idempotency result per key, and no draft access for the
delivery role.

## Interfaces

- Repository types implementing the domain's store, outbox and idempotency ports.
- Auth's session and credential stores.
- A migration runner used by `colophon admin migrate` (operator mode only).

## Failure modes

| Situation | Behaviour |
|---|---|
| Serialization failure or deadlock | Retry the whole transaction up to 3 times, then a safe 409 or 503; observable as a metric |
| Pool exhausted | 503 with `Retry-After`; the queue never grows without bound |
| Connection lost during `COMMIT` | The outcome is unknown; the client retries with the same idempotency key and learns the real result (F02) |
| Database down | Writes fail honestly; nothing is acknowledged from a local queue |
| Disk pressure | Optional growth is rejected at 85%; unsafe writes are blocked before 90% (spec §33) |

## Tests and evidence

- Integration tests against the local stack's PostgreSQL 18 (CI runs the same stack), each in a fresh database
  with migrations applied, as the application login (`crates/colophon-db/tests/isolation.rs`).
- Two concurrent saves on one base revision.
- A duplicate idempotent submission, and a different payload under the same key.
- A cross-project reference rejected by a foreign key; two projects with colliding slugs and IDs.
- Two concurrent releases on the same base generation.
- A crashed worker whose lease expires; a late finalize from the old lease is rejected.
- RLS: the API role cannot read another project's rows even with a forged ID; context resets across pooled
  connections.
- Failed commits, and migrations on an empty and on a fixture database.

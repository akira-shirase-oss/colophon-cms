# 02 · db (`crates/colophon-db`, `migrations/`)

> The PostgreSQL adapter. Constraints and transactions make invalid states impossible to store, even if application
> code has a bug.

## Why it exists

PostgreSQL is the only source of truth. Checks in the API alone race: two requests can both pass a precheck. Uniqueness,
references, generation order and lease ownership therefore have to be enforced by the database, inside short
transactions.

## End goal

Every domain port has a Postgres implementation whose constraints back up the domain invariants. Concurrency, crash and
cross-project tests pass against a real PostgreSQL 18 container, and every migration is reviewed, forward-only and
tested on an empty database and on a fixture database.

## Responsibilities

- Migrations and the database role model.
- Tables, constraints and indexes.
- Transaction boundaries and retries.
- The outbox, inbox and idempotency storage.
- Row-level security context.
- Full-text search.
- The published projections that the delivery role reads.

## Not its job

- Deciding rules. It enforces the domain's rules; it does not invent new ones.
- External calls.
- Caching (handled by [delivery](06-delivery.md)).

## Breakdown

### Migrations (spec §12)
- SQLx migrations in reviewed SQL, forward-only.
- Large changes follow **expand → backfill → contract**.
- Steps that cannot run in a transaction (for example `CREATE INDEX CONCURRENTLY`) are marked and tested separately.
- A migration lock, statement and lock timeouts, and checkpointed backfills that can stop and resume.
- Compatibility is kept with the current and the previous application version during rolling updates.

and IDs sort by creation time.

### Constraints that carry invariants
- **Composite foreign keys** over `(project_id, environment_id, id)`, so a reference can never cross a project or
  environment (D3).
- **Insert-only revisions:** no `UPDATE`/`DELETE` grants for application roles (D1).
- **Slug claims:** unique per project, environment, collection and locale, with explicit lifetimes for draft
  reservations and published routes.
  - Built in step 3.6 (D-054, migration 0016): each revision stores its slug; `entries.draft_slug` copies the draft's
    and `publications.slug` the published revision's. Two partial unique indexes are the claims:
    `entries_draft_slug` (drafts of live entries, since migration 0030) and `publications_live_slug` (open
    publications). A violation of either is `DbError::SlugTaken`. The draft copy is kept equal to the draft revision's slug by the two statements that move the
    draft pointer, not by a foreign key; a test holds it. Locales join the key when they exist.
- **Publication history:** candidate design is an `int8range` column with an exclusion constraint per entry and
  locale. That requires the `btree_gist` extension; the alternative is application checks under a lock (D5).
- **Idempotency:** unique `(actor, scope, operation, key)` plus a stored request hash. The result is written in the
  same transaction as the effect. Ordinary keys are kept at least 7 days.
  - Built in step 1.2 as `idempotency_records`. The key is **claimed first** (`INSERT … ON CONFLICT DO NOTHING`): a
    concurrent duplicate waits on the unique index for the first request, then replays its committed answer, or claims
    the key if the first rolled back. Only successes are recorded (D-035).
- **Draft pointers** (step 1.2): `entries.draft_revision_id` is a deferred composite foreign key to
  `revisions (project_id, environment_id, entry_id, id)`, so it can only name one of the entry's own revisions; a
  revision's base is checked the same way (D3).

### Transactions (spec §08)
- **Save (built in step 1.2):**
  - `SELECT … FROM entries WHERE … FOR UPDATE` locks the entry, so concurrent saves queue; if the pointer isn't the
    expected revision, return "stale" with the current one, having written nothing;
  - insert the revision with the expected revision as its base;
  - `UPDATE entries SET draft_revision_id = $new WHERE … AND draft_revision_id = $expected`, the rule itself (D2);
  - all in one transaction, together with the idempotency record (below).
  - Since step 3.6 (D-055), a save or a create first takes the collection's content-type lock shared
    (`content_types::lock_for_write`), before it reads the content type.
- **Content type change (built in step 3.6, D-055):** take the collection's content-type lock exclusively
  (`content_types::lock_for_change`, a transaction-scoped advisory lock keyed on project, environment and collection),
  then read the current version; for a narrowing change, check every draft and every published revision that isn't a
  draft (`stored_page`, in pages, at most 10,000 in all); insert the next version. Writes and publishes in the collection
  hold the same lock shared, so none can slip between the check and the commit.
- **Release commit:**
  - since step 3.6, take the content-type lock of every collection in the changeset, shared and in order, before
    reading its items;
  - lock the environment row (`SELECT … FOR UPDATE`) and check the base generation;
  - insert the release and its items;
  - close and open publication intervals;
  - advance the generation;
  - write the audit and outbox rows;
  - commit.
- **Isolation:** short READ COMMITTED transactions with explicit locks. Multi-row invariants use deterministic lock
  ordering or SERIALIZABLE, retrying **the whole transaction** at most 3 times, then returning a safe conflict or
  transient error.
- Never retry only the last statement, and never hold a transaction open across an external call.

### Outbox and leases (spec §16)
- Outbox rows are inserted in the same transaction as the change that caused them.
- Workers claim bounded batches with `FOR UPDATE SKIP LOCKED` and set lease owner, expiry and attempt generation.
- Finalizing is a conditional update on the lease owner and attempt generation (D9).

### Row-level security and roles (spec §08, §13)
- **Roles:**
  - the migration login owns the tables and runs `colophon admin migrate` (locally the stack's `colophon` user; in
    production a dedicated owner role that is not a superuser);
  - `colophon_api`, `colophon_worker` and `colophon_delivery` are privilege roles with least privilege and no login.
    Migrations grant to them; step 1.1 created `colophon_api`;
  - each process logs in as its own role that is a member of exactly one privilege role (locally `colophon_app` in
    `colophon_api`, created by `deploy/postgres/roles.sql`).
- `colophon_delivery` reads published projections only and can never read draft tables. Built in step 2.2 (D-045):
  `deploy/postgres/roles.sql` creates it and grants it to `colophon_app` without inheritance; a delivery
  transaction runs `SET LOCAL ROLE colophon_delivery`, which leaves it only `SELECT` on `publications`, `releases`
  and environments' generations, in the requested project's context. `colophon_worker` (step 2.3, D-046) is switched
  to the same way and sees jobs in every project, their destinations, releases, and which entries a release
  changed (not their content).
- A project's own roles (who may do what in the product, not database roles) are rows: `roles` and
  `role_permissions` (migration 0017, D-058), versioned and editable since migration 0018. Members can read their
  project's roles before its context is set, because the membership lookup loads the caller's permissions in the
  same statement. The owner role's row and permissions refuse every update and delete (0018's triggers). Memberships
  name a role through a foreign key; invitations don't (old ones are history), so inviting holds a shared advisory
  lock on the role and deleting one takes it exclusively and counts pending invitations (docs/modules/03-auth.md).
- References (migration 0024, D-065): `revision_references` keeps each revision's references, inserted with it and
  never changed, with foreign keys to the revision and to `entries (project, environment, id, collection)`, so none
  names a missing entry or one of another collection. `entries::insert_revision` prechecks them for a precise
  `MissingReference` (field and place); the foreign key is the rule. `releases::commit` refuses a release that leaves a
  published entry naming an unpublished one, or takes down an entry a published entry names
  (`Committed::Broken`), checking only the release's own items.
  Since migration 0025 (step M.3) `field` is a path (`sections/1/by`): field ids and list positions, at most 400
  characters. `entries::referrers` finds each reference's entry and open publication by revision, through
  `entries_by_draft_revision` and `publications_open_by_revision` (migration 0028), one `LATERAL ... LIMIT 1` lookup
  apiece: joined plainly, a generic plan scanned the environment's entries once per reference.
- Single types (migration 0026, D-067): `entries.single` copies the type's flag at creation (read inside the
  INSERT), and the partial unique index `entries_single` allows one such entry per collection
  (`DbError::SingleExists`); `content_types::set_single` counts and flips the flags under the type's exclusive lock.
- Shared components (migration 0029, D-073): `components` and insert-only `component_versions`, like content types;
  `colophon_db::components` reads, creates and versions them, finds the content types whose current definition holds
  the marker `"component":"<slug>"` (`users`), and takes advisory locks of their own class: `lock_for_use` (shared,
  sorted) before a content type's change lock, `lock_for_change` (exclusive) before the locks of the types a change
  rewrites. Migration 0029 also lets `component.create` and `component.update` hold idempotency keys.
- Unique fields (migration 0027, D-070): `unique_claims` holds one row per entry, unique field and side (draft or
  published) that sets a value, with the SHA-256 of the value's JSON text; the constraint `unique_claims_value` on
  (collection, field, side, hash) is the rule (`DbError::ValueTaken`). `colophon_unique_fields(definition)` reads a
  definition's unique field ids (without parsing one that has none) and `colophon_unique_values(fields, content)` a
  document's claims (PL/pgSQL, so empty `fields` never parses the content). Claims exist only for the current
  version's unique fields and move with what they describe: `entries::create`/`save` replace the draft's as they move
  the draft pointer, `releases::commit` replaces the published claims of every entry in the release after its
  publications change, and `content_types::claim_unique` drops the claims of fields no longer unique and, in one
  statement, claims the values of newly unique fields unless two drafts or two publications share one (then it
  returns them and claims nothing). `entries::unique_holder` names the entry in the way for the refusal's wording.
- API tokens and the audit log (migration 0023, D-063): `api_tokens` (one project, a SHA-256 hash, a kind, an expiry
  within 366 days, revoked never deleted, an identity of its own) and `api_token_permissions` (like
  `role_permissions`, with a CHECK refusing the four people-only actions); `audit.read` joins the actions and every owner
  holds it. Both token tables are bound to the project's context by row-level security; `api_tokens`' is enabled, not
  forced, so `colophon_api_token(hash)` (`SECURITY DEFINER`, owned by the migration login) finds a token before its
  project is known. `audit_events` takes inserts and reads from the application only, and a trigger refuses updates,
  deletes and truncation from anyone. `colophon_db::{tokens, audit}`, `scope::begin_as_token`; `tests/tokens.rs`
  proves the log refuses the owner and the application alike, that a revocation waits for a running request, and that
  a token is invisible outside its project.
- Deleting entries (migration 0030, D-080): `entries.deleted_at` and `deleted_by` (an identity: a person or an API
  token's own; a CHECK keeps them set together). Nothing is ever removed: the row becomes a tombstone.
  - Row-level security on `entries` is split by command: `entries_live` (SELECT) and `entries_changed` (UPDATE) let
    `colophon_api` see and change only live entries of the project; `entries_created` (INSERT) refuses a deleted one.
    Every query the API runs therefore treats a deleted entry as missing. Foreign keys are checked without row-level
    security, so revisions, `revision_references`, `changeset_items`, publications and tombstones that name it stay
    valid.
  - `entries_draft_slug` and `entries_single` are recreated as partial indexes that also require
    `deleted_at IS NULL`: a deleted entry's slug and its single type's place are free, while `draft_slug` still copies
    its draft's slug.
  - `colophon_delete_entry(project, environment, entry, collection, expected, event)` is the only way to delete:
    `SECURITY DEFINER`, `search_path = pg_catalog, pg_temp`, `EXECUTE` revoked from `PUBLIC` and granted to
    `colophon_api`. It refuses to run unless `project` is the transaction's `app.project_id` (and an identity is set),
    locks the live entry `FOR UPDATE`, and returns `not_found`, `stale` (with the draft), `published`, `referenced`
    (another live entry's draft, or an open publication, names it; a self-reference doesn't count), `in_changeset` (a
    changeset without a release pins it) or `deleted`; only then it sets `deleted_at`/`deleted_by` to the transaction's
    identity, deletes the entry's `unique_claims` and inserts the `entry.deleted` audit event. Each check is its own
    statement, so it sees everything committed before the lock was granted. `colophon_db::entries::delete` takes the
    content type's shared lock first (D-055), calls it, and on a refusal reads the referrers or the pending
    changesets for the answer.
  - Its owner is `colophon_deleter`, a no-login role that is a member of `colophon_api` (so it has exactly the API's
    privileges and policies) plus two policies of its own on `entries` (`entries_deleter_sees`: the project's deleted
    entries too; `entries_deleter_tombstones`: a live entry may become a tombstone) and the only `UPDATE` grant on the
    two columns. Not the table owner: `entries` forces row-level security on its owner and no policy names it.
    PostgreSQL checks an UPDATE's new row against the SELECT policies too, which is why the API's role can't write the
    tombstone itself. The migration creates the role if it is missing, tolerating a concurrent creation, and
    `deploy/postgres/roles.sql` creates it with the others.
  - The trigger function `colophon_entry_live()` runs `BEFORE INSERT` on `revision_references` and `publications` and
    `BEFORE INSERT OR UPDATE OF revision_id` on `changeset_items`: it locks the named entry `FOR KEY SHARE` and raises
    a foreign-key violation named `<table>_entry_live`, with the entry's id as its detail, if the entry is deleted.
    That lock conflicts with the deletion's `FOR UPDATE`, so a new reference, pin or publication and a deletion never
    both commit; the loser fails cleanly (`DbError::MissingReference`, `DbError::EntryDeleted`). The deletion's own
    UPDATE changes no key column, so it takes only `FOR NO KEY UPDATE`, which `FOR KEY SHARE` doesn't wait for: the
    explicit `FOR UPDATE` is what makes them meet.
  - `changeset_items_by_entry` indexes items by entry, for the `in_changeset` check. `changesets::items` and the
    changeset list join entries with `LEFT JOIN`, so a published changeset keeps listing an item whose entry was
    deleted (`created_by` is then `None`).
  - `tests/deletion.rs` runs each race with two real transactions in both orders (a save adding a reference, a raw
    insert that skips the precheck, a changeset pin, a publication, a release committing first), and checks the
    tombstone, the refusals, what comes free, and that the function refuses another project's context.
- Setup codes (migration 0020, D-061): `setup_codes` holds each code's SHA-256 hash, expiry and who used it, and
  `setup_attempts` the last fifteen minutes of attempts. The application role can't touch either, nor
  `installation` or `administrators`: it calls `colophon_issue_setup_code`, `colophon_setup_attempt`,
  `colophon_live_setup_codes` and `colophon_claim_setup_code`, `SECURITY DEFINER` functions that refuse everything
  once `colophon_installation_set_up()` is true. `colophon_db::setup` wraps them; `tests/setup.rs` proves each
  property against real Postgres.
- Application roles never own tables and never hold `BYPASSRLS` or superuser rights. Policies use `FORCE ROW LEVEL
  SECURITY` where appropriate.
- Context is set per transaction (`set_config('app.project_id', …, true)`). Tests prove it resets correctly on pooled
  connections.
- In step 1.1, `scope::begin(pool, Scope { identity, project })` opens every project-scoped transaction. Projects,
  environments and memberships force RLS; a project is visible only inside its own context or to its members.
  Identities, sessions and sign-in attempts aren't project-scoped: the application reaches them only through
  `colophon_db::identity`, with column-level `UPDATE` grants.
- Step 1.7 (migration 0005, D-042): owners change and remove memberships inside the project's context
  (`scope::begin_as_member` returns the caller's role with the transaction). `UPDATE (role)` and `DELETE` are granted
  on memberships, and the deferred constraint trigger `memberships_keep_an_owner` refuses a commit that leaves a
  project without an owner. `invitations` isn't project-scoped for the person accepting, who isn't a member yet; the
  application reaches it only through `colophon_db::members`, by token hash or from an owner's transaction.
- Step 1.8 (migration 0006, D-043): `installation` (one permanent row: who was bootstrapped and when; triggers refuse
  update, delete and truncate, even by the owner) and `administrators`. `colophon_api` reads both and writes neither;
  `colophon_db::administrators::bootstrap` runs as the migrator. The restrictive policy
  `projects_created_by_administrators` refuses a project inserted for anyone who isn't an administrator.
- Step 2.1 (migration 0007, D-044): `changesets`, `changeset_items` (each pins a revision of its own entry, by a
  composite foreign key) and `reviews` (insert-only, with a per-changeset `seq`), all project-scoped with forced row
  level security. The application may update a changeset's hash and submission and an item's revision; reviews only
  ever grow.
- Step 2.2 (migration 0008, D-045): `releases` (one row per generation; a changeset publishes once), `publications`
  (a copy of each published revision with its half-open generation interval; an exclusion constraint over
  `int8range(valid_from, valid_to)` per entry, using `btree_gist`), and `UPDATE (generation)` on environments for the
  conditional bump.
- Step 2.3 (migration 0009, D-046): `destinations` and `jobs` (the outbox: inserted with the release; a lease
  owner, expiry and generation; `UNIQUE (destination, generation)`; partial indexes for due and leased jobs).

### Pools and timeouts
- Pools: API 16 connections (`COLOPHON_DB_MAX_CONNECTIONS`), worker 10 (reference profile). Throughput of the
  signed-in path grows with the pool, because each connection mostly waits on round trips; size it per deployment.
- Acquire timeout 2 s; statement timeout 5 s (`PoolSettings`); explicit longer budgets only for administrative jobs.
- No ping on checkout; sqlx pings on release and drops broken connections (D-033).
- A full pool returns 503 with `Retry-After` (`DbError::Busy`), never an internal error (D-033).
- Keep round trips per request low: decide in Rust whether a write is needed (the session touch), and read what one
  response needs in one transaction (`identity::profile`).
- Measured cost of content types (step 1.5): loading and parsing the collection's current definition on every entries
  request took the drafts scenario from 1,893 to 1,698 requests/s on the reference laptop. Caching definitions by
  `(project, environment, collection, version)` is the obvious next optimisation once it matters.
- Prepared statements and growing tables (step 2.4): sqlx keeps every statement prepared on its connection, and after
  five runs Postgres may switch it to one generic plan that it keeps until the next `ANALYZE`. A plan chosen while a
  table is nearly empty can be a full scan inside a per-row lookup, and it stays as the table grows: the changeset
  list (a lateral lookup of each changeset's newest review) slowed to 200 ms within a 40-second CI load test. A query
  with lookups per row over tables that grow quickly sets `SET LOCAL plan_cache_mode = force_custom_plan` in its own
  transaction (`changesets::list`), so it is planned on every run with the tables as they are; a test checks it never
  runs on a generic plan. Not set globally: planning every statement would cost more than it saves.

### Search (spec §18)
- PostgreSQL full-text search (generated `tsvector` columns and GIN indexes), scoped by project, environment and locale.
- Results respect the same field and revision visibility as everything else.
- There is no separate search service until measurements justify one.

### Retention (spec §27)
- Unpinned revisions and resolved delivery metadata: 90 days.
- Terminal ordinary jobs: 30 days.
- Idempotency records: at least 7 days. Nothing deletes them yet (step 1.2); the retention job will, using the
  `idempotency_records_by_age` index.
- Audit: 90 days.
- A legal hold blocks deletion for its exact scope.
- The deletion ledger is copied off-host for replay after a restore.

## Invariants enforced here

D1 (grants), D2 (conditional update), D3 (composite foreign keys), D4 (row lock plus check), D5 (exclusion constraint
or locked check), D9 (conditional finalize), plus: one idempotency result per key, and no draft access for the
delivery role.

## Interfaces

- Repository types implementing the domain's store, outbox and idempotency ports.
- Auth's session and credential stores.
- A migration runner used by `colophon admin migrate` (operator mode only).

## Failure modes

| Situation | Behaviour |
|---|---|
| Serialization failure or deadlock | Retry the whole transaction up to 3 times, then a safe 409 or 503; observable as a metric |
| Pool exhausted | 503 with `Retry-After`; the queue never grows without bound |
| Connection lost during `COMMIT` | The outcome is unknown; the client retries with the same idempotency key and learns the real result (F02) |
| Database down | Writes fail honestly; nothing is acknowledged from a local queue |
| Disk pressure | Optional growth is rejected at 85%; unsafe writes are blocked before 90% (spec §33) |

## Tests and evidence

- Integration tests against the local stack's PostgreSQL 18 (CI runs the same stack), each in a fresh database
  with migrations applied, as the application login (`crates/colophon-db/tests/isolation.rs`, `entries.rs`).
- In place since step 1.2: save and history; a stale save writes nothing; two concurrent saves on one base (one wins,
  the other is stale, its revision never stored); revisions can't be changed or deleted; a draft pointer can't name
  another entry's revision; another project sees no rows even by id; idempotent replay, mismatch, keys per operation
  and per person; a concurrent duplicate waits and replays.
- Two concurrent saves on one base revision.
- A duplicate idempotent submission, and a different payload under the same key.
- A cross-project reference rejected by a foreign key; two projects with colliding slugs and IDs.
- Two concurrent releases on the same base generation.
- A crashed worker whose lease expires; a late finalize from the old lease is rejected.
- RLS: the API role cannot read another project's rows even with a forged ID; context resets across pooled
  connections.
- Failed commits, and migrations on an empty and on a fixture database.

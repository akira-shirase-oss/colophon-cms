> look and behave like one product.

## Why it exists

Three frontends drift apart quickly without shared tokens. Accessibility is also easier to get right once, in shared
components, than three times. Material Design 3 (D-011) supplies a complete, documented design language: colour roles,
typography, shape, elevation, state layers and motion. Colophon implements it as owned tokens and components rather than
depending on a component framework.

## End goal

One M3 token set and one library of owned components that every frontend uses, with light, dark and high-contrast
schemes generated from the brand seed, accessibility built in, and every deviation from the M3 specs recorded.

## Responsibilities

- M3 design tokens as CSS custom properties and a Tailwind theme.
- Owned Svelte components built on Bits UI primitives and styled to M3.
- Accessibility defaults: focus rings, contrast, reduced motion, target sizes.
- A record of deviations from M3 and of local overrides.

## Not its job

- Page layouts. Each app owns its own navigation and layout.
- Content rendering ([content-renderer](12-content-renderer.md)).
- The public blog's visual identity. The blog may use these tokens, but its look is its own
  ([web-blog](15-web-blog.md)).

## Breakdown

### Colour (M3 colour roles)
- Generated with `@material/material-color-utilities` from one brand seed colour (O-016).
- Roles: primary, secondary, tertiary, error, surface containers, outline, inverse, and their `on-*` pairs.
- Schemes: light and dark, plus medium and high contrast levels.
- Generated once at build time into CSS custom properties (`--md-sys-color-*`), never computed in the browser on each
  page load.
- Contrast between every role and its `on-*` pair is checked in CI.
- The logo stays monochrome ([brand](../brand/README.md)); colour comes from the scheme.

### Typography, shape, elevation, motion
- **Typography:** the M3 type scale (display, headline, title, body, label) as tokens. The typeface is chosen at P0,
  self-hosted, and has no external font requests.
- **Shape:** the M3 corner scale (none → full) as tokens.
- **Elevation:** tonal surface containers first; shadows only where M3 uses them.
- **Motion:** M3 easing and duration tokens. Everything respects `prefers-reduced-motion`.
- **State layers:** hover, focus, pressed and dragged opacities as tokens, so every interactive component behaves the
  same way.

### Components
- Built on **Bits UI** headless primitives, which provide keyboard handling, focus management and ARIA. Components
  include buttons, icon buttons, text fields, selects, menus, dialogs, sheets, tabs, chips, snackbars, tooltips,
  progress indicators, lists and navigation rail/drawer.
- Styled to the M3 component specs, using only the tokens above.
- **O-015:** `m3-svelte` (Apache-2.0 OR GPL-3.0-only, single maintainer) may supply complex components if it passes the
  accessibility, bundle-size and bus-factor review. Whatever is adopted is copied or pinned, and owned.
- **Not used:** `@material/web` (maintenance mode pending new maintainers, per its README, checked 2026-10-25) and MUI
  (React-only).

### Studio-specific patterns
- The five publishing labels (Saved, Published in CMS, Website update pending, Verified at configured locations, Needs
  attention) map to M3 roles consistently: neutral, primary, tertiary, success (custom role), error.
- The delivery-receipt timeline, the release slider and the conflict screen are composed from the base components.

### Editor theme settings
- Editors may change approved theme settings only (for example the seed colour or the type scale). They can never paste
  JavaScript or arbitrary Svelte into content (spec §19).

## Invariants

| ID | Invariant |
|---|---|
| U1 | Every interactive component is keyboard-operable, labelled and visibly focused. |
| U2 | Motion respects the reader's reduced-motion setting. |
| U3 | Components use tokens only; there are no hard-coded colours, radii or durations. |
| U4 | Every colour role and its `on-*` pair meets the contrast target for its scheme. |

## Interfaces

- Token CSS (`--md-sys-*` custom properties) and a Tailwind preset.
- Svelte components imported by each app.
- A token build script: seed colour → schemes → CSS.

## Failure modes

| Situation | Behaviour |
|---|---|
| A chosen seed colour produces weak contrast | The CI contrast check fails; the seed or the contrast level changes |
| An upstream library (Bits UI, `m3-svelte`) changes | Overrides and pinned versions are listed, so the merge is reviewed rather than blind |
| M3 guidance changes | Recorded as a deliberate update with before/after screenshots |

## Tests and evidence

- Component tests in Vitest.
- Automated accessibility checks on every component, in light, dark and high-contrast schemes.
- The contrast check for every colour role pair.
- Visual checks of the first Studio screen against the M3 specs at phone and desktop widths.

## Build order

1. **P0:** the token build script, colour schemes, type and shape scales, base components, the first screen. Built in
   step 0.7: `packages/ui` (`theme.json`, the generator, `tokens.css`, `base.css`, components on Bits UI) and the
   Studio's editor screen on it (D-024, D-025).
2. **P1:** the components the editor needs (text fields, menus, dialogs, snackbars, the conflict screen parts).

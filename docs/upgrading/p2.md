# Upgrading to P2: migrations 0007 to 0010

Applies to a database at migration 0006 (the end of P1) or partway through P2, moving to `main` at the end of
milestone P2: step 2.4, merged on 2026-10-26 as `c38ec47`. Time: not measured; these migrations add tables and indexes
and backfill nothing. Downtime: yes, the server is stopped while they run.

Colophon is pre-release, with no versioned releases or binaries: upgrading means building from a later commit and
applying its migrations. `colophon admin migrate` applies every migration its build knows, so a build from today's
`main` carries on through P3; read [p3.md](p3.md) too.

## Before you start

- [ ] Finish [p1.md](p1.md) first if `_sqlx_migrations` stops before 6.
- [ ] Note the commit you run now (`git rev-parse --short HEAD`); every crate is version 0.0.0.
- [ ] Take a copy of the database you could restore. There is no supported backup yet (P6).
- [ ] **Create the two new database roles before migrating**: `colophon_delivery` (migration 0008 grants to it) and
      `colophon_worker` (0009). Neither logs in; the server's login, `colophon_app`, must hold both with
      `INHERIT FALSE, SET TRUE`. On the local stack, run `scripts/stack.sh up` once more: it applies
      [`deploy/postgres/roles.sql`](../../deploy/postgres/roles.sql), which is safe to rerun. Elsewhere, run the
      same statements as a role that may create roles.
- [ ] Make sure the `btree_gist` extension is available (PostgreSQL's contrib package): migration 0008 creates it.

## Are you affected?

As the migrator:

```sql
select coalesce(max(version), 0) as newest from _sqlx_migrations where success;
```

`newest` from 6 to 9: this guide applies. 10 or more: go on to [p3.md](p3.md).

And check the roles before you start:

```sql
select rolname from pg_roles
where rolname in ('colophon_api', 'colophon_app', 'colophon_delivery', 'colophon_worker')
order by rolname;
```

All four must be there. With one missing, migration 0008 or 0009 stops with `role "colophon_delivery" does not exist`
(or `colophon_worker`); that migration is rolled back and the ones before it stay applied, so create the role and run
the migrations again.

## What changes for you

- **Editors:** you gather the versions you want to publish into a *publish request* (a changeset) and ask for review;
  an approval counts only for exactly those versions, so editing afterwards needs a fresh approval (2.1). Publishing
  an approved request makes a release with the next number (its generation); if someone else published first, you
  are told rather than overwriting them (2.2). Each release can be announced to your website by a webhook (2.3).
- **Developers:**
  - changesets under `{P}/changesets`: create, submit, refresh, review and publish, each publish idempotent;
  - `{P}/releases`, the release list;
  - public delivery at `/content/v1/{project}/{environment}/{collection}`, read-only and without sign-in, at the latest
    release or pinned with `?generation=`, every answer naming its release in `Colophon-Generation` (2.2);
  - `{P}/destinations` for webhooks and `{P}/jobs` for their deliveries; a receiver gets `release.committed` with an
    `Idempotency-Key` that is the same on every retry, so it must deduplicate by that key (2.3).
- **Operators:**
  - the worker runs inside the server: `--role all` (the default) and `--role worker` run it, `--role api` doesn't;
    `--role worker` still serves the API too, so give each process its own `COLOPHON_LISTEN_ADDR`;
  - new settings `COLOPHON_WORKER_POLL_MS`, `COLOPHON_WORKER_LEASE_MS`, `COLOPHON_WORKER_SLOTS` and
    `COLOPHON_WORKER_DB_CONNECTIONS` (2.3), and `COLOPHON_WORKER_ATTEMPT_MS` (2.4), which must be shorter than the
    lease or the server refuses to start;
  - the worker opens its own pool of `COLOPHON_WORKER_DB_CONNECTIONS` (4) on top of the API's 16;
  - webhooks must be `https://` and public, unless the server listens on a loopback address.

## Steps

1. Stop the worker if it runs on its own (there is none before step 2.3), then every other `colophon-server` process.
2. Create the roles (above).
3. Build the server and the CLI from the commit you are moving to:

   ```sh
   cargo build --release --locked -p colophon-server -p colophon-cli
   ```

4. Apply migrations 0007 to 0010 as the migrator. They are additive: new tables (`changesets`, `changeset_items`,
   `reviews`, `releases`, `publications`, `destinations`, `jobs`), new indexes and grants, and an environment's
   `generation` made writable by the application. Nothing existing is rewritten.

   ```sh
   COLOPHON_MIGRATION_DATABASE_URL=postgres://colophon:PASSWORD@HOST:5432/colophon \
     target/release/colophon admin migrate
   ```

   On the local stack: `scripts/migrate.sh`.
5. Start the API, then the worker (or one `--role all` process).
6. Wait until `colophon doctor --server URL` exits 0.

## Check it worked

- `_sqlx_migrations` shows 7 to 10, each `success`.
- `colophon doctor --json` reports the role you started (`all` or `worker`), so you know the worker is in the process.
- In a scratch project: write an article, add it to a publish request, submit it, approve it as an owner or publisher,
  and publish. Then:

  ```sh
  curl -i https://cms.example.com/content/v1/PROJECT_ID/production/articles
  ```

  answers `200` with `Colophon-Generation: 1` and the article.
- With a webhook destination on that project, `GET {P}/jobs?generation=1` lists its job as `succeeded`, and your
  receiver got one `release.committed` (or more with the same `Idempotency-Key`, if an attempt's answer was lost).

## Rolling back

- **Before step 4:** run the commit you noted.
- **After it:** there are no down migrations; restore the copy you took, and lose every publish request, review,
  release and delivery made since.
- Webhooks already delivered can't be taken back. After a restore, releases that were announced may be numbered again
  for different content: tell receivers, or start them from scratch.

## Known issues

- **An older local stack lacks the roles.** `colophon_delivery` arrived with step 2.2 and `colophon_worker` with 2.3;
  rerun `scripts/stack.sh up` before `scripts/migrate.sh` (AGENTS.md, [deploy/README.md](../../deploy/README.md)).
- **Webhooks aren't signed yet** (D-046): receivers can drop duplicates by `Idempotency-Key` but can't verify the
  sender.
- **The worker polls.** With nothing to do it sleeps `COLOPHON_WORKER_POLL_MS` (500 ms) between looks; there are no
  wake-ups yet (O-010).
- **Per-project and per-destination limits from module 05 aren't enforced**, beyond one announcement in flight per
  destination (0010).
- **A killed worker's deliveries wait for their lease** (`COLOPHON_WORKER_LEASE_MS`, 30 s) before another claim
  repeats them with the same key, and each repeat uses one of the job's 5 attempts.

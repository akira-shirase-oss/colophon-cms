# Upgrading to P3: migrations 0011 to 0015

Applies to a database at migration 0010 (the end of P2) or partway through these, moving to `main` as of 2026-10-27:
P3 steps 3.1 to 3.5 and the title-search fix (`065e614`, migration 0015). P3 itself isn't finished: steps 3.6 to 3.8
are still being built or planned, and their migrations are in [unreleased.md](unreleased.md). Time: not measured;
0015 rewrites every entry once and builds an index over them, so it grows with the number of entries. Downtime: yes,
the server is stopped while the migrations run.

Colophon is pre-release, with no versioned releases or binaries: upgrading means building from a later commit and
applying its migrations.

## Before you start

- [ ] Finish [p1.md](p1.md) and [p2.md](p2.md) first if `_sqlx_migrations` stops before 10. P2's two database roles
      must exist.
- [ ] Note the commit you run now (`git rev-parse --short HEAD`); every crate is version 0.0.0.
- [ ] Take a copy of the database you could restore. There is no supported backup yet (P6).
- [ ] Make sure the `pg_trgm` extension is available (PostgreSQL's contrib package): migration 0015 creates it.
- [ ] If your migrator isn't a superuser, it must be a member of `colophon_delivery`: migration 0011 makes that role
      the owner of a function. The local stack's migrator is a superuser and needs nothing.
- [ ] Decide whether to run Valkey. From step 3.1, `COLOPHON_CACHE_URL` caches public answers, not only readiness.

## Are you affected?

As the migrator:

```sql
select coalesce(max(version), 0) as newest from _sqlx_migrations where success;
```

`newest` from 10 to 14: this guide applies. 15: you are on today's `main`. 16 or more: the database was migrated by a
branch; see [unreleased.md](unreleased.md).

To estimate how long 0015 takes, count what it rewrites:

```sql
select count(*) from entries;
```

## What changes for you

- **Editors:**
  - you can take an article off the website through the same review as publishing; old links to it stop working,
    and the Studio shows *removal pending at the CDN* until the CDN accepts the purge (3.2);
  - every release gets one label, the receipt: *Published in CMS*, *Website update pending*, *Verified at N
    locations* or *Needs attention*, with every check behind it (3.3);
  - the Studio is redesigned; you can search titles, compare any two versions and see what changed in a publish
    request (3.5).
- **Developers:**
  - `/content/v1` answers are cached by release, and carry `ETag` (a matching `If-None-Match` gets `304`),
    `Cache-Control`, `Cache-Tag` and `Colophon-Cache: hit | miss | coalesced | bypass` (3.1);
  - an unpublished entry answers `410` `gone` at every generation, and lists leave it out (3.2);
  - destinations take a `kind`: `webhook` (the default), `cdn`, which gets `POST {"tags": [...]}` (3.2), or
    `probe`, which is fetched and must show the release in a `Colophon-Generation` header or a
    `<meta name="colophon-generation" content="N">` marker, optionally pinned to a `location` (3.3);
  - `GET {P}/releases/{generation}` is the receipt: `label`, `locations`, each destination's part and every probe
    observation; the release list gains `purge`, `label` and `locations` (3.3);
  - `GET {P}/collections/{collection}/entries?q=` searches titles, at most 100 characters (3.5).
- **Operators:**
  - `COLOPHON_CACHE_URL` now serves public reads from Valkey; without it they come from PostgreSQL;
  - `COLOPHON_WORKER_LOCATION` (default `local`) names where each worker runs, for probes (3.3);
  - the worker now also purges CDNs and runs probes; a probe's "not yet" is retried every 5 s or more, up to 10
    attempts;
  - the local Keycloak shows Colophon's sign-in theme (3.5).

## Steps

1. Stop the worker if it runs on its own, then every other `colophon-server` process.
2. Build the server, the CLI and the Studio from the commit you are moving to:

   ```sh
   cargo build --release --locked -p colophon-server -p colophon-cli
   npm ci && npm run build -w @colophon/studio
   ```

3. Apply migrations 0011 to 0015 as the migrator. 0011 to 0014 add a function, columns with defaults, two tables
   (`tombstones`, `observations`), indexes and grants, and widen which destination kinds are allowed. 0015 adds
   `entries.draft_title`, fills it from every entry's draft, makes it required and builds a trigram index on it; the
   `entries` table is locked while it runs.

   ```sh
   COLOPHON_MIGRATION_DATABASE_URL=postgres://colophon:PASSWORD@HOST:5432/colophon \
     target/release/colophon admin migrate
   ```

   On the local stack: `scripts/stack.sh up` (for the sign-in theme), then `scripts/migrate.sh`.
4. Start the API, then the worker (or one `--role all` process).
5. Wait until `colophon doctor --server URL` exits 0. With `COLOPHON_CACHE_URL` set, its cache check must say `up`;
   `degraded` means Valkey isn't reachable and public reads are coming from PostgreSQL.

## Check it worked

- `_sqlx_migrations` shows 11 to 15, each `success`.
- Every entry has its draft's title:

  ```sql
  select count(*) from entries where draft_title is null;
  ```

  answers 0 (the column is `NOT NULL`, so the migration couldn't have finished otherwise).
- In a scratch project with a probe destination pointing at a page of your site that carries the generation marker
  (the reference site from `scripts/demo.sh` does), publish a change. Its receipt, `GET {P}/releases/{generation}`,
  reaches `"label": "verified"` with `"locations": 1` once the site has rebuilt. Without a probe the label stays
  `published`: nothing checked the site, and the receipt says so.
- With Valkey configured, read the same public list twice:

  ```sh
  curl -si https://cms.example.com/content/v1/PROJECT_ID/production/articles | grep -i colophon-cache
  ```

  The first answer says `miss`, the second `hit` (for a list with at least one article: empty answers are served but
  never cached).
- Search for the article's title in the Studio's entry list: it is found.

## Rolling back

- **Before step 3:** run the commit you noted.
- **After it:** there are no down migrations; restore the copy you took, losing what was written since. Don't run an
  older server against the migrated database: after 0015 it can't create entries, because `entries.draft_title` is
  required and it doesn't write it.
- Purges and announcements already sent can't be taken back. Empty the cache after a restore: its keys name a
  generation the restored database may number again for different content.

## Known issues

- **Purge requests carry no credentials yet.** A `cdn` destination works with an endpoint that accepts Colophon's
  `{"tags": [...]}` unauthenticated, like the fake CDN in the tests; there is no adapter for a real CDN's API yet.
  A purge that fails for good leaves copies until they expire (30 s for latest answers, 300 s for pinned ones), and
  the release's `purge` says `failed`.
- **One location by default**, so receipts say *verified at 1 location*. A probe sees one URL at one moment: it can't
  say that every page or every CDN edge updated (D-051).
- **Shared caches may hold a latest answer for up to 30 s** until a purge reaches them (D-048).
- **A big `entries` table makes 0015 slow**, and writes to it wait until it is done. Grown local databases are the
  likeliest place to notice: on 2026-10-27 the maintainer's local database had grown to 5 GB from repeated test runs.
  Use a fresh database (`COLOPHON_TEST_DATABASE`) for development rather than migrating a large one.
- **A Keycloak container from before 3.5 lacks the sign-in theme** until `scripts/stack.sh up` recreates it with the
  theme mounted.

# Upgrading to P1: migrations 0001 to 0006

Applies to a database with none of migrations 0001 to 0006, or only some of them (P0 had no database schema), moving to
`main` at the end of milestone P1: step 1.8, merged on 2026-10-26 as `2652f43`. Time: not measured; seconds on an
empty database on the local stack. Downtime: yes, the server is stopped while the migrations run.

Colophon is pre-release. There are no versioned releases or binaries, so "upgrading to P1" means building from a later
commit and applying its migrations. `colophon admin migrate` applies **every** migration its build knows: built from
today's `main`, it goes straight on through P2 and P3. That is fine; read [p2.md](p2.md) and [p3.md](p3.md) before you
start, because P2 needs two more database roles to exist first.

## Before you start

- [ ] Note the commit you run now (`git rev-parse --short HEAD`): every crate is version 0.0.0 until v0.1, so
      `colophon-server --version` can't tell you.
- [ ] Take a copy of the database you could restore. There is no supported backup yet (P6); the docs site's
      *Backups and restore* page explains what a plain `pg_dump` does and doesn't give you.
- [ ] Have an OpenID Connect provider ready (Keycloak in the local stack): from step 1.1 nobody can use Colophon
      without signing in.
- [ ] Make sure the database roles exist: the migrator (the tables' owner), `colophon_api`, and the server's login
      `colophon_app` as a member of `colophon_api` without `BYPASSRLS`. On the local stack `scripts/stack.sh up`
      creates them from [`deploy/postgres/roles.sql`](../../deploy/postgres/roles.sql); migration 0001 creates
      `colophon_api` itself only if the migrator is allowed to create roles.

## Are you affected?

Run this as the migrator:

```sql
select coalesce(max(version), 0) as newest
from _sqlx_migrations
where success;
```

- `relation "_sqlx_migrations" does not exist`: the database has never been migrated. This guide applies.
- `newest` below 6: this guide applies.
- `newest` 6 or more: you are past P1; go on to [p2.md](p2.md).

After the migrations, check whether anyone may create projects:

```sql
select count(*) from administrators;
```

Zero means the installation hasn't been bootstrapped yet: step 4 below.

## What changes for you

- **Editors:** you sign in through your organisation's identity provider (1.1). Every save is a new version that
  never changes, and the draft points at the latest (1.2). If someone saved since you started, your save is refused
  and the Studio shows both versions instead of merging silently (1.3). Articles follow a content type (1.5). Owners
  invite people with single-use links that last 72 hours, and give each person a role: owner, developer, editor or
  publisher (1.7). Only the installation's administrator creates projects (1.8).
- **Developers:** the management API, `/api/v1`, arrives: projects, entries and their versions with `If-Match` and
  `Idempotency-Key`, content types, members and invitations, `/me`. Browser writes need an `Origin` the server trusts
  and an `X-CSRF-Token`. The CLI signs in with a device code approved in the Studio and gets a bearer token for 30
  days: `colophon login`, `logout`, `whoami`, `content create`, `content list` (1.6).
- **Operators:**
  - the server needs `COLOPHON_DATABASE_URL` to be the application's login (`colophon_app`), never the owner's;
    row-level security applies to it;
  - sign-in needs `COLOPHON_PUBLIC_URL` and all three of `COLOPHON_OIDC_ISSUER`, `COLOPHON_OIDC_CLIENT_ID` and
    `COLOPHON_OIDC_CLIENT_SECRET`; `COLOPHON_TRUSTED_ORIGINS` adds origins allowed to send cookie-authenticated writes;
  - `COLOPHON_STUDIO_DIR` serves a Studio build at `/studio` (1.3);
  - `colophon admin migrate` and `colophon admin bootstrap` run as the migrator, with
    `COLOPHON_MIGRATION_DATABASE_URL`.

## Steps

1. Stop every `colophon-server` process. (P1 has no worker yet.)
2. Build the server and the CLI from the commit you are moving to, and the Studio if you serve it:

   ```sh
   cargo build --release --locked -p colophon-server -p colophon-cli
   npm ci && npm run build -w @colophon/studio
   ```

3. Apply the migrations as the migrator. They are additive except one backfill: 0003 gives every environment the
   built-in `articles` content type and records every existing revision as an article of its version 1.

   ```sh
   COLOPHON_MIGRATION_DATABASE_URL=postgres://colophon:PASSWORD@HOST:5432/colophon \
     target/release/colophon admin migrate
   ```

   On the local stack, `scripts/migrate.sh` does this and step 4 in one go.
4. Make the first administrator, bound to the identity provider's issuer and their subject there (`colophon whoami`
   shows it once they have signed in; it works before that too):

   ```sh
   target/release/colophon admin bootstrap --subject SUBJECT --issuer https://id.example.com/realms/main
   ```

   It works once per installation; for the same person again it changes nothing.
5. Start the server and wait until it is ready:

   ```sh
   target/release/colophon doctor --server https://cms.example.com
   ```

   Exit code 0 means `/readyz` says `ready`.

## Check it worked

- The migration table shows 1 to 6, each `success`:

  ```sql
  select version, description, success from _sqlx_migrations order by version;
  ```

- The administrator signs in to the Studio and can create a project; someone else signed in can't.
- From a terminal, the CLI signs in and writes the same draft the Studio does:

  ```sh
  colophon login --server https://cms.example.com
  colophon whoami
  colophon content create articles --project my-site --json --data '{"title":"Upgrade check","body":{"schema":"colophon/rich-text","version":1,"doc":{"type":"doc","content":[{"type":"paragraph","content":[{"type":"text","text":"Written after the upgrade."}]}]}}}'
  colophon content list articles --project my-site --json
  ```

  The new entry appears in the Studio at once. The built-in article needs both a title and a rich-text body.

## Rolling back

- **Before step 3:** run the commit you noted.
- **After it:** there are no down migrations. Restore the copy you took; anything written since is lost.
- `colophon admin bootstrap` can't be undone, even by the table owner, without dropping the `installation` table's
  triggers on purpose ([migration 0006](../../crates/colophon-db/migrations/0006_administrators.sql)).

## Known issues

- **A Keycloak started before step 1.8 has random user ids**, so `dev-owner` isn't the subject `scripts/migrate.sh`
  bootstraps. Recreate it: `docker compose -f deploy/compose.yaml up -d --force-recreate keycloak`
  ([deploy/README.md](../../deploy/README.md)).
- **A database bootstrapped for the wrong person stays that way.** Bootstrap runs once; on a test install, start again
  from an empty database.
- **The development client secret refuses to run off loopback.** With `colophon-dev-client-secret`,
  `COLOPHON_LISTEN_ADDR` must be a loopback address; register a real client for anything else.
- **The session cookie is always `Secure`.** Anywhere but `localhost`, serve the server through HTTPS (a TLS proxy in
  front), or browsers won't keep the session.
